# 需求澄清

配合 mv-engineering-doc-writer 的写作模式使用。目标是在起草 PRD/HLD/LLD/RFC 之前补齐事实、约束与决策边界，不把推测写成需求。文档结构仍按 document-types 执行。

## 澄清清单

| 维度 | 要确认的内容 |
| --- | --- |
| 目标 | 解决的问题、业务价值、成功判据；不把方案当目标 |
| 用户与角色 | 谁使用、谁审批、谁运维；权限与数据可见范围 |
| 范围 | In Scope / Out of Scope；本期不做什么 |
| 业务流程 | 触发条件、主流程、异常流程、人工介入点 |
| 业务规则 | 状态流转、计算口径、时限、优先级、例外 |
| 数据 | 来源、字段、精度、保留期、敏感级别、迁移 |
| 集成 | 上下游系统、协议、频率、失败处理、责任边界 |
| 非功能 | 规模、性能、可用性、合规、审计、部署环境 |
| 验收 | 可验证的验收标准与证据形式 |

## 干系人与术语

- 列出业务方、使用方、运维方、外部系统责任方；写明谁有权确认需求、谁负责验收。
- 建立领域术语表：术语、定义、同义词、禁用词、与系统字段的对应关系；全文统一使用。
- 行业术语保留原文，不强行翻译；不确定含义时向用户确认，不按字面猜测。

## 业务流程与规则

- 用「触发 → 步骤 → 判断 → 结果」描述主流程；异常与补偿单独写。
- 业务规则写成可判定的条件与结果，不写「合理处理」「适当提示」。
- 规则冲突时列出冲突点与影响，交由用户裁决；不自行取舍后隐藏。
- 区分已确认规则、假设与待确认项；假设必须可验证，待确认项有责任人与期限。

## 验收标准

- 每条需求至少一条可验证的验收标准；写清输入、动作、预期结果与证据。
- 涉及权限、审计、国际化、并发、失败恢复的需求，验收标准覆盖对应场景。
- 不把「页面能打开」「接口返回 200」当作业务验收。

## 输出

澄清产出：需求清单（编号、描述、优先级、验收标准）、术语表、流程与规则、假设与开放问题、干系人与确认记录。缺失信息标 `Open Question`，不编造。

需求澄清只补事实与约束；PRD/HLD/LLD 的文档结构归 document-types，架构决策归 mv-architecture-standards，安全要求归 mv-security-standards。
