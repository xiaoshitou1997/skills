# 工程文档与图件

将工程文档与图件作为独立交付物产出，而不是当前对话的延伸。按交付物分三个任务模式；一项任务跨模式时在同一 skill 内按「写作编排内容 → 制图产图 → 插图编排进文档」顺序完成，不把中间产物误作交付完成：

- **写作模式**：文档内容与结构——新建、局部修订、重写、评审。
- **制图模式**：可编辑图源与本地渲染成品图片，图本身即交付物，不管图最终进不进文档。
- **插图编排模式**：把图源或成品图放进 Markdown/Word/PPT——插图、换图、尺寸与位置控制、图文一致与文档内核验。

## 脚本位置

`SKILL_ROOT` 必须显式设为本次加载的 skill 目录，不能假设环境已提供；脚本路径恒加引号。命令从用户项目目录执行，不在 skill 目录内产生运行时文件。

```bash
SKILL_ROOT="/实际绝对路径/mv-engineering-doc-writer"
python3 "$SKILL_ROOT/scripts/layout_gen.py" --help
bash "$SKILL_ROOT/scripts/render_diagram.sh" --help
python3 "$SKILL_ROOT/scripts/office_figures.py" --help
```

## 写作模式

### 核心流程

1. 确定任务模式：
   - 新建（Create）：依据需求、笔记、源文件、代码或讨论产出新文档。
   - 局部修订（Update）：维护现有文档中的指定内容，并同步直接受影响的引用、表格或图；补字段、改步骤等请求默认按此模式处理。
   - 重写（Rewrite）：用户明确要求全文重写或规范化时，把既有草稿整体整理为可评审的工程文档。
   - 评审（Review）：识别缺陷、歧义、缺失决策、前后矛盾、不可验证的论断和运维缺口。
2. 从用户意图判断文档类型，适用时优先按 PRD、HLD、LLD、RFC、API 或 MOP 处理。
3. 起草前先对输入语句分类：
   - Fact（事实）：已确认的系统行为、数据、代码、配置、接口或实测结果。
   - Requirement（需求）：明确要求的行为或约束。
   - Decision（决策）：已明确选定的方案或取舍。
   - Assumption（假设）：设计所需但未经验证的条件。
   - Open Question（开放问题）：未决的决策或缺失的输入。
   - Discussion（讨论）：探索性内容，不得静默升级为需求。
4. 仅从 `references/document-types.md` 加载与本次相关的结构。生产升级/部署流程类任务同时加载 `references/mop-guide.md`。
5. 起草过程遵循 `references/quality-rules.md`。
6. 交付前执行 `references/self-check.md` 的最终检查。

只要能安全产出有用的草稿，就不为缺失细节反复追问；用 `TBD`、`Assumption`、`Open Question` 或显式占位符代替编造取值。

### 来源忠实

当源文件、截图、工单、会议纪要、代码或用户提供的文本是文档依据时：

- 只陈述来源能够支撑的内容。
- 保留既有的术语、标识符、端点名、配置键、版本号和职责边界。
- 不静默修正、调和或扩展来源未支持的内容。
- 补充外部知识或推理时，与来源推导的内容明确区分。
- 除来源本身是应列入 `References` 的正式引用外，最终文档不暴露源文件名、聊天记录或起草过程。

### 内容规则

- 文档脱离当前对话仍可独立理解。
- 使用客观的工程语言。
- 同一概念全文使用同一个稳定术语。
- 需求与实现选择分开；决策与备选方案、未决问题分开。
- 关键论断在有证据（代码、配置、接口、需求、数据、日志或正式引用）时可追溯到证据。
- 宁可显式标注未知，不用看似合理的补全。
- 设计决策有明显成本或风险时给出权衡。
- 范围可能被扩大时给出 `In Scope` 与 `Out of Scope`。
- 不为“看起来完整”添加空洞章节。

### 默认文风

默认使用中文工程书面语，用户另有要求除外。

- 不用“我们”“你”“您”等人称措辞。
- 不用“根据您的要求”“以下是”“结合之前讨论”“本次调整”等对话痕迹用语。
- 不用“高性能”“高可用”“先进”“优雅”等无依据的夸饰。
- 不用“搞”“弄”“东西”“到时候”“回头”“搞定”等口语。
- 中英文与数字边界保持可读，如 `TLS 1.3`、`P99 18 ms`、`Redis 集群`。
- 优先朴素的 Markdown；不用装饰性 emoji、过量强调和装饰性分隔线。
- 架构、流程、时序用图能显著提升理解时使用 Mermaid。

### 文档类型行为

#### PRD

聚焦问题、目标用户/角色、目标、范围、需求、验收标准、依赖和开放问题。不把实现想法过早写成需求。

#### HLD

聚焦系统上下文、架构、组件、边界、接口、数据流、部署拓扑、主要非功能约束、故障域和关键权衡。实现细节保持在架构评审所需的层次。

#### LLD

聚焦模块/类/组件行为、详细流程、数据模型、接口、状态迁移、校验、错误处理、并发/幂等、配置、可观测性和可测试的实现细节。

#### RFC

让决策过程显式化。包含问题、目标/非目标、方案、已考虑的备选、理由、影响/权衡、兼容性/迁移、风险和未决问题。决策未定时写 `Decision: TBD`。

#### API 文档

精确描述契约行为：用途、端点或 RPC 名、方法、路径、认证、请求字段、响应字段、状态/错误码、校验规则、幂等、示例，以及来源支持的兼容性/版本策略。绝不虚构请求字段或错误码。

#### MOP

升级/部署 MOP 是可执行的生产变更操作文件，不是泛泛的升级介绍。仅在已确认时包含前置条件、变更范围、准备项、备份、逐步命令/动作、检查点、成功标准、回滚触发条件、回滚步骤、变更后验证和责任人。加载 `references/mop-guide.md`。

### 局部修订行为

- 起草前确定修改目标及直接影响范围，沿用既有章节、编号、术语与文风，保持已确认的需求、设计与接口语义。
- 文档类型模板用于检查本次内容的必要信息，不要求旧文档补齐所有章节、重新编号或统一全文格式；不因修改某一节而重写其他章节。
- 同步修改直接受影响的字段说明、交叉引用、示例与图表，确保修订内容可独立理解并与关联内容一致。
- 质量规则与最终检查按修订内容及其直接影响范围应用；新建与明确要求全文重写时检查整个交付物。无关历史问题单列建议，不自动修订。
- 例如新增一个 API 响应字段时，同步该字段的定义与响应示例，不顺带替换 API 文档结构或补写无来源的认证与版本策略。修复相关矛盾必须扩大范围时，先说明影响并确认范围。

### 重写行为

重写既有文档时：

- 除非用户要求变更设计，保持已确认的含义不变。
- 清除对话痕迹、无依据假设、重复章节、术语漂移和形式化套话。
- 只解决明显的结构缺陷，不改变事实。
- 除非用户要求，不输出变更日志。
- 矛盾无法依据材料裁断时，两侧都保留，并标记为 `Open Question`。

### 评审行为

只评审不重写时，按影响分级：

- Critical：可能导致错误实现、不安全的生产执行、不兼容的 API 行为、数据丢失或不可恢复的变更。
- Major：缺失决策、前后矛盾、责任/边界歧义、关键论断不可验证、回滚或失败处理不完整。
- Minor：术语、格式、措辞、局部可读性或可维护性问题。

每条发现说明问题、影响和具体修改建议。不为展示修改能力而虚构项目事实。

## 制图模式

把已确认的事实制成规范图：物理组网图画设备与连线实体，逻辑组网图画网段、安全域与流量路径，架构图画组成部分与依赖方向，一张图只表达一个层面；时序、流程、状态、ER 等结构类图用文本图源表达。图中事实来自用户提供的资料与逐项确认，不替用户发明组件与连接。

`判定图种与要素 → 选图源 → 绘制图源 → 渲染成图 → 核验交付`

- 交付落在目标项目的 `fig-src/`（图源）与 `fig-out/`（成品图）；图后续进文档时，插图编排模式直接使用同一目录与命名约定，无需迁移。
- 制图无独立运行时状态目录，不在 `~/.mv/` 下落状态。

工作流：

1. 判定图种与要素：明确图的用途与受众（评审、HLD 附件、汇报、交付档案），按 [图种与要素清单](references/diagram-elements.md) 判定图种，并对照该图种必备要素逐项核对来源资料——设备与型号、位置分区、链路两端与端口、带宽、网段、组件与调用方向、交互顺序等。缺的要素先向用户与项目资料取得，取得不了的按「待确认」标注并说明缺什么，不编造取值。
2. 选图源：需要精确摆放的图（组网图、机架连线图、架构分层图、页面示意）用 HTML+内联 SVG，坐标由 layout_gen 从 spec 生成；时序、状态、ER、类图与结构简单的流程图用 Mermaid，需要特定 UML 语法时选 PlantUML。画法判定（通道分配、对称、布局取舍）按 [图面语法](references/visual-grammar.md)，画法与渲染细节按需读取 [SVG 图源与渲染](references/svg-diagrams.md)。
3. 绘制图源：精确摆放的图先写 spec（JSON，格式见 `layout_gen.py --help`），运行 `python3 "${SKILL_ROOT}/scripts/layout_gen.py" spec.json "fig-src/<图名>.html"` 生成自包含图源；本机无 mermaid CLI 时时序图用 layout_gen 的 sequence 模板。生成器断言失败（文字超宽、直落不在目标框内等）按报错回改 spec 重跑，不绕过；生成器未覆盖的局部才在产物上手调，手调不破坏网格与间距。图源不引用外网资源，组件与链路命名与用户资料术语一致。修改先改 spec 或图源。
4. 渲染成图：优先使用当前会话已配置的浏览器预览/截图能力；无该能力时用 `render_diagram.sh` 发现本机 Chrome/Edge 无头渲染，窗口尺寸与图源画布一致，倍率按目标用途设定（评审与文档用图 ≥2x）。浏览器缺失时如实报告缺失，保留图源并注明未渲染，不虚构成品。
5. 核验交付：打开成品核对文字不溢出、连线不穿节点、图例完整、方向一致，并逐项回对来源事实；交付说明写出图源与图片位置、依据哪些资料、待确认要素清单、渲染方式与核验结果。

### 制图硬约束

- **先要素后画图**：组件、连接与标注必须来自用户确认的资料；缺要素的链路标「待确认」并说明缺什么，不编造端口、IP、带宽、网段。
- **物理与逻辑不混画**：同一张图不同时表达设备实体与网段/流量语义；确需对照时画两张，图元命名保持对应。
- **图源可再生成**：交付必须含可编辑图源；只有 PNG 不称可编辑图源；修改先改图源再渲染，不直接修改成品图。
- **先算法后坐标**：精确摆放的图必须先写 spec 由 layout_gen 生成，禁止无算法徒手摆坐标；状态、ER 等带环路的图交给 Mermaid/PlantUML 自动布局，不用本生成器硬画。
- **本地渲染**：不把含真实组网信息的图源上传在线渲染服务；不使用隐式联网安装依赖的 `npx`。
- **披露最小化**：内网地址、设备型号按用户披露范围呈现，不向图外扩散；产物只写在用户项目内。
- 冲突时按用户明确需求 → 本规范 → 工具默认行为处理。

## 插图编排模式

负责图在目标文档中的放置与验证：插图、换图、尺寸与位置控制、图文一致与成品核验；文档正文、结构和事实核验由写作模式负责，图的绘制与渲染由制图模式产出（`fig-src/` 与 `fig-out/` 命名对应）。

工作流程：

1. 确定文档格式、图的目的与插入位置，核对成品图与正文术语一致。已有文件先查看目标页、段落或形状，明确图尺寸；图标编号与图注由写作模式维护。
2. 需要新图时，先走制图模式完成可编辑图源与成品图片；已有图或已有截图直接进入放置。按需读取 [渲染指南](references/rendering.md) 做文档侧嵌入判定与图片核验。
3. Markdown 在目标阅读器支持时可直接嵌入 Mermaid 源码，否则引用已渲染的本地图片。Word/PPT 使用已渲染的 PNG，在**写作文档的同一任务中**插入成品，不把制图完成误作交付完成。
4. 对新建的 Word/PPT，先用该格式的文档制作能力生成正文或幻灯片，再在确定的位置插图；对已有文件先列举目标图或设置唯一锚点，再插入或替换。按需读取 [Office 配图指南](references/office-figures.md)。本模式脚本编辑图形，不生成任意正文或整套幻灯片。
5. 写出新的文档文件后，复查图文一致、图注、比例、位置、裁切、与页面背景的对比和文件可打开性。能使用目标应用时逐页查看；只运行了 ZIP/XML 检查时如实记录尚未进行视觉检查。

### 插图编排硬约束

- 换图先换保留的图源并重渲染（制图模式的渲染流程），不直接修改成品图；真实页面截图保持来源与时间可追溯。发现成品图与正文事实不一致时停下核对来源，不为版面美观补造或修改图的内容。
- 处理含敏感信息的图不上传在线服务。依赖缺失时报告缺失，不默默调用会联网安装依赖的 `npx`。
- 保持目标格式可用。Office 文件只能向**不同的输出路径**写入；先预览定位候选项，目标不唯一时停止，绝不以“图注前最近一张图”自动修改。
- Word/PPT 替换只改变被选中的一张图；即便几处共用同一媒体文件，也不能覆写原媒体使其他位置一起变化。
- 不把 Markdown 的 Mermaid 块直接当作 Word/PPT 图片交付；图源、图片、目标文档三者均应存在且对应。
- 冲突时按用户明确需求 → 本规范 → 工具默认行为处理；用户指定的图源格式、布局和现有项目约定优先。

## 产物组合

用户明确要求 DOCX、PDF、幻灯片等渲染产物时，先由写作模式确定内容与结构，再用相应的能力生成目标文件格式。写文档需要配图时，写作模式编排内容并核对图文事实：先制图模式产出可编辑图源与渲染成品，再由插图编排模式插入并核验；Markdown 正文中的内联 Mermaid 块属于正文写作，由写作模式直接撰写。上游业务梳理（端到端业务流程、规则与验证场景）由用户提供的材料承担，材料缺失处按 `TBD` 与 `Open Question` 标注，不自行编造业务流程。
