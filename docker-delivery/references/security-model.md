# Docker 交付安全模型

脚本使用调用者或 agent 的权限运行。Skills 提供操作指导与工具，不承担沙箱、授权网关或云端密钥存储的职责。

## 控制措施

1. **用户授权**：生产部署/回滚、强制 Git 操作、数据库变更和远端写入需要明确的用户意图。常规生产变更未带 `--approve-prod` 时脚本会拒绝执行，但该参数不能证明用户已经授权。
2. **平台控制**：本仓库不安装命令 Hook。团队控制由 agent 权限、项目 Hook、仓库分支保护和 CI 落实，skill 指令本身不是强制执行机制。
3. **秘密信息**：项目 `.env.dev`、`.env.prod` 和私钥不得进入 Docker 构建上下文、Git 或命令日志。用户负责权限与密钥存储。暂存审计检查文件名和明显的秘密内容，不能替代 Gitleaks 或凭据扫描。
4. **生产验证**：传输前后不可变镜像 ID 必须一致，默认要求已验证的 dev 收据，生产必须有真实健康信号（Docker 健康检查或 HTTP 探活）。收据只记录本工作机执行的验证，不是签名证明。
5. **失败恢复**：部署验证失败时，执行脚本尝试恢复上一个镜像。数据/数据库迁移、新环境配置和外部副作用不会自动撤销；回滚后检查服务实际状态。
6. **可选扫描策略**：`FF_REQUIRE_SECURITY_SCAN=1` 要求构建时使用 Trivy，源码扫描时另用 Gitleaks。CI 应落实严格策略，不能将跳过扫描解释为通过。

## 部署前提

dev 与 prod 使用不同的 SSH 目标和隔离的应用目录。主机密钥按 SSH 的 `known_hosts` 机制验证，不禁用该检查。限制 Docker daemon 的访问权限，查看 `docker compose config` 时避免输出秘密信息；不将不可信的镜像名或环境值传入部署命令。
