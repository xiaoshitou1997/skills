# 架构形态与一致性判定

配合 mv-architecture-standards「关键规则」使用。判定按当前业务与团队事实，不为未来假设提前拆分；判据命不中时保持更简单的形态。

## 系统形态

| 形态 | 适用条件 | 不适用信号 |
| --- | --- | --- |
| 单入口单服务 | 一个团队、一套发布节奏、单库可承载、无独立伸缩或网络边界 | 两端需要独立发布/伸缩；单库写入成为瓶颈；合规要求数据物理隔离 |
| 按端切 | admin 与 user 需要独立发布、独立伸缩或独立网络暴露 | 两端始终同版发布；拆开后大量共享事务 |
| 按域切（微服务） | 多个域有独立团队、独立发布、独立数据所有权；域间以事件/接口协作 | 域间强事务；团队没有独立运维能力；跨服务调用链过长 |
| 模块化单体 | 默认形态：单仓多模块，模块边界清楚，单进程部署 | 模块间仍共享表、跨模块直接调用内部实现——说明边界没划清，不是拆服务的理由 |

判定顺序：先看团队与发布边界，再看数据所有权，最后看技术伸缩；技术伸缩可以通过垂直扩容、读写分离、缓存缓解，不单独构成拆分理由。

## 同步与异步

| 场景 | 默认选择 | 说明 |
| --- | --- | --- |
| 用户请求需要立即结果 | 同步 | 明确超时、重试与降级；不把长耗时操作塞进请求链路 |
| 通知、审计、统计、索引更新 | 异步事件 | 接受最终一致；消费端幂等；死信可观测 |
| 跨团队/跨系统集成 | 同步接口或事件按契约 | 接口用于查询与命令，事件用于状态变更广播；不双写 |
| 长流程、多步骤、需要补偿 | 编排式 Saga 或状态机 | 每步幂等、可重试、可查询；不依赖分布式事务 |
| 削峰 | 消息队列 | 队列深度、消费延迟、积压告警进设计 |

## 一致性

- 单库单事务能解决时不引入跨服务一致性机制。
- 跨服务写：优先 Outbox（本地事务写业务表与事件表，异步投递），消费端幂等；需要补偿时用 Saga，写明补偿动作与不可补偿的外部副作用。
- 读模型允许延迟时用事件投影或定时对账；对账任务必须有差异告警与修复入口。
- 不把「最终一致」当作不实现的理由：必须写明延迟上限、失败可见性与人工介入路径。

## 多租户

| 模型 | 适用 | 代价 |
| --- | --- | --- |
| 单租户独立部署 | 客户少、合规要求强、版本可独立 | 运维成本随客户数增长 |
| 独立库/独立 schema | 中等客户数、需要数据隔离 | 迁移与连接池管理复杂 |
| 共享表 tenant_id | 客户多、标准化 SaaS | 所有查询与唯一约束必须带租户；跨租户泄露风险最高 |

共享表模型的硬要求：租户上下文在入口层确定并贯穿全链路；数据访问层强制注入租户条件；唯一索引包含租户列；后台任务与导出按租户隔离；管理端跨租户操作单独授权并留审计。

## 数据边界

- 每个服务/模块拥有自己的表；跨边界读走接口、事件或只读模型，不直连对方数据库。
- 报表与检索不直接压业务库：用只读副本、物化视图、数仓或搜索索引，并写明同步延迟。
- 数据保留、归档与删除在方案阶段定；涉及个人信息与合规数据时，先过 mv-security-standards 的数据分级。

## 演进

- 接口与数据变更走 expand–contract：先加兼容字段/新表，双写或回填，切读，最后删除旧路径；每一步可独立发布与回滚。
- 大重构拆成可发布的小批次，每批保持系统可运行；不合并「架构调整 + 业务功能」为一个不可回滚的大变更。
- 旧系统下线前写明流量切换、数据迁移、回滚与观察期。

本文只给判定与取舍；版本选型归 mv-tech-stack-baseline，代码分层归 mv-backend-standards 与 mv-frontend-standards。
