# 架构规范

面向 mv 团队自研系统的架构决策与评审：定系统边界、依赖方向、一致性与集成方式，并把决策落成可执行的 ADR 与评审记录。版本选型、代码分层、文档排版与部署编排不归本 skill。

## 作用与优先级

这是**规范型 Skill**，在需求已确认、进入方案设计与架构评审时引用；不负责技术栈选型、接口字段设计、编码实现与部署。优先级：用户明确需求与项目已采纳的规范 / ADR → 本规范 → 生态默认。

架构决策先于实现。涉及跨模块、跨服务、跨团队、数据隔离或不可逆迁移的决策，先写 ADR 再开工；能在单模块内解决的，不上升为系统级决策。

## 开始前确认

开始前确认：业务目标与核心用例、预期规模（用户量、数据量、峰值）、可用性与恢复目标（RTO/RPO）、合规与数据敏感级别、团队规模与发布节奏、既有系统与外部集成边界。未确认先问，不默认微服务、多租户或消息队列。

## 关键规则

1. **默认模块化单体**：单仓多模块、按端或按域切片；单入口能支撑时不拆服务。不做「看起来干净」的拆分。
2. **拆分判据**：出现独立团队、独立发布节奏、独立伸缩需求、独立网络边界或独立数据合规边界之一，才拆为独立服务；拆分的收益必须大于分布式事务、网络故障与运维成本。
3. **边界与数据所有权**：每个模块或服务拥有自己的数据，不跨边界直接读表；跨边界只经接口或事件。共享代码放 common 或按端 api 模块，不把业务逻辑塞进共享库。
4. **依赖方向单向**：接入层 → 领域层 → 基础设施；领域层不反向依赖接入层，不依赖具体框架的 Web 组件；跨层调用与循环依赖视为架构缺陷。
5. **同步默认，异步按需**：请求-响应能表达且延迟可接受时用同步；需要解耦、削峰、跨团队异步或长流程时才引入消息队列。异步链路必须设计幂等、重试、死信与可观测性。
6. **一致性显式化**：单库本地事务优先；跨服务一致性用 Outbox、Saga 或对账，不默认引入分布式事务；写明业务可接受的延迟与失败补偿方式。
7. **外部集成走防腐层**：第三方 SDK、协议与数据模型不直接渗透到领域层；在边界处转换成本方模型，统一超时、重试、熔断、限流与验签。
8. **多租户默认关闭**：确有多个客户共享一套部署时，按合规与规模选择隔离模型（独立库、独立 schema、共享表 tenant_id）；所有查询强制租户过滤，唯一约束含租户，跨租户管理走单独授权。
9. **非功能约束进设计**：容量、可用性、恢复目标、可观测性、成本与数据保留在方案阶段明确；关键指标不能等到运维阶段补。
10. **演进可回退**：接口与数据结构按 expand–contract 演进，先兼容后收紧；大改拆分批次，每批可独立发布与回滚；不一次性大爆炸重构。
11. **决策留痕**：影响面跨模块、不可逆或存在多个可行备选的决策写 ADR；ADR 记录背景、决策、备选、影响与回滚，不记录讨论过程。
12. **评审看失败模式**：架构评审不只画组件图，逐项检查边界是否清楚、依赖是否单向、数据是否归属明确、失败与重试是否可收敛、权限与租户是否隔离、观测与回滚是否具备。

## 输出

方案阶段产出：简版 ADR（一项决策一份）、架构评审记录（结论、风险、开放问题、责任人）、需要回填到 HLD/LLD 的约束清单。未确认的规模、合规与集成细节标 `TBD` 或 `Open Question`，不编造取值。
