# 可读性修剪清单

编码规范合规是交付前置；本清单处理「合规但不优雅」的部分，在交付前对本次变更直接影响范围执行一遍修剪。每条信号给出判定标准与修法；判定不过且不修剪的项在交付说明记录原因。优先级：用户明确需求与项目既有约定 → 本清单 → 个人风格偏好。

## 结构信号

- 单一抽象层次：一个方法内全部语句处于同一粒度——要么全是业务步骤，要么全是技术细节，不混层。判定：逐行读出声是同一份提纲；业务步骤与技术细节交错即混层。修法：把技术细节块提炼为命名表意的方法。
- 复杂度预算：单方法 ≤30 行，单方法分支（if、case、循环）总数 ≤10；嵌套深度按 [java-guide.md](java-guide.md)「常量、控制语句与注释」的 3 层卫语句条款判定。超预算且提炼方法无法降到预算内时，在交付说明说明原因。
- 万能词命名：类与方法名删掉后，仅凭所在类与调用上下文说不出其职责，即判为万能词命名，修法是换业务动词与业务名词（词表见 [java-guide.md](java-guide.md)「代码与命名」）。
- 重复三遍才抽象：同一段逻辑第二次重复先容忍，第三次出现时提炼；新抽象必须有至少两个现役使用点或已确认的第二个变更方向，不为「将来可能」提前抽象。
- 注释补位判定：需要注释向读者解释「这段在做什么」时，先改名或提炼方法再考虑保留注释；解释「为什么」的注释保留。注释条款见 [java-guide.md](java-guide.md)「常量、控制语句与注释」。
- 模型对齐：类、方法、字段与状态名使用 mv-design-standards 需求分析确认的业务术语，代码不另造同义词；代码词汇与业务规则文档对得上。

## 修剪流程

1. 规范合规先行：先过 [java-guide.md](java-guide.md)「交付自查清单」，合规项不重复修剪。
2. 逐条过结构信号：对本次新增或实质修改的方法逐条判定；存量代码按最小变更原则不追溯，仅本次触碰的方法不达标时顺带修剪。
3. 删除项清理：未用 import、注释掉的旧实现按 java-guide 条款删除。
4. 复跑验证：修剪是行为等价变换，完成后复跑编译与受影响测试；行为有变的不是修剪，按 SKILL.md「测试」分节补测试后另行提交。
5. 记录：交付说明列出修剪点（文件与方法）、对应信号、未修剪项及原因；未执行明确写「未执行」。

## 反目标

- 过度抽象：抽象必须有至少两个现役实现或已确认变更方向；单实现的策略模式与形式化接口+实现两件套按主规范「分层与命名」条款不加。
- 为优雅而重写：判据是新人可读、改动落点单一，不是行数更少或技巧更炫；无关代码不追溯达标。
- 修剪保持行为等价是硬边界；借修剪夹带行为变化按重构流程处理并补测试。

边界：本清单是编码规范的补充，不替代静态检查与测试；项目已有可读性与重构约定优先。
