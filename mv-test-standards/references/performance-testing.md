# 性能与负载测试

配合 mv-test-standards 使用。性能测试回答「在什么负载下、哪条链路、以什么阈值、是否达标」，不是一次性的跑分。项目没有明确性能目标时，先与用户确认目标，再设计测试。

## 何时执行

- 有明确吞吐、延迟、并发或容量目标的功能与接口。
- 高并发、大促、批量导入、报表导出、消息积压等风险场景。
- 架构变更、数据库索引/查询调整、缓存策略变更、依赖升级后的回归。
- 上线前容量评估与扩容决策。

## 负载模型

先写清楚再压测：

| 项 | 内容 |
| --- | --- |
| 业务场景 | 登录、列表、下单、支付回调等核心链路 |
| 负载曲线 | 稳态并发、峰值并发、爬坡时间、持续时间 |
| 数据规模 | 表行数、租户数、热点分布、冷热比例 |
| 请求配比 | 各接口占比、读写比例、 payload 大小 |
| 环境 | 与生产同量级的数据库/中间件；注明差异 |
| 阈值 | P95/P99 延迟、错误率、吞吐、资源水位 |

不拿开发机单机压测结果当生产容量结论；环境差异必须写进报告。

## 场景设计

- 单接口基线：先测单请求延迟与资源消耗，再叠加并发。
- 混合场景：按真实配比混合读写、缓存命中与未命中、同步与异步链路。
- 峰值与过载：超过预期峰值时的降级、限流、错误码与恢复行为。
- 稳定性：持续负载下内存、连接池、GC、队列积压是否收敛。
- 数据增长：在目标数据量级下测，不用空库结论。

## 工具与证据

- 工具按项目栈选择（k6、JMeter、Gatling 等），不因规范更换既有工具；脚本与数据版本化。
- 报告写：环境与版本、负载模型、场景、阈值、实际结果、瓶颈与资源曲线、失败请求样例。
- 区分压测客户端瓶颈与被测系统瓶颈；客户端资源打满时结论无效。
- 未执行的压力测试写「未执行」，不把单接口基准当容量结论。

## 常见问题

- 只压读不压写，忽略事务、锁与唯一约束。
- 用缓存命中率极高的数据压测，生产冷启动后性能骤降。
- 忽略异步链路与消息积压，只测同步入口。
- 压测数据不清理，影响后续测试与共享环境。
- 只看平均值，不看 P95/P99 与错误率。

性能测试的组织与证据归本文件；容量与架构决策归 mv-architecture-standards，运行期指标与告警归 mv-ops-standards。
