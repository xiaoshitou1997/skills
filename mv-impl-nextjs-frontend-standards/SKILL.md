# 前端规范

## 作用与优先级

这是**规范型 Skill**，在 Agent 编码、审查、测试期间引用；不负责流程编排，不负责构建出包、镜像与启动调试。适用于前端项目：通用条款对任意前端框架适用，Next.js/React 专属条款仅在使用对应框架时应用，不向其他框架强加不兼容约束。

优先级：用户明确需求和项目已正式采纳的规范 / ADR → 本规范 → 框架默认约定。

## 开始前确认

开始前确认本次页面/组件范围、需求或设计稿来源、目标框架与渲染模式（静态导出或 SSR），不默认原型、旧文档或现有代码永远权威。代码用于说明当前实现；与已确认设计不一致时记录差距，不反向改写设计。

## 关键规则

1. 组件分层：页面（路由层）只做组装与数据编排；可复用 UI 组件无业务副作用；业务逻辑进 hooks/services，不在组件体内堆叠。一个文件一个组件，命名与职责一致。
2. 类型契约：组件 props、API 响应、全局状态一律显式 TypeScript 类型；API 响应类型与后端契约字段一一对应，不随手 `any`；不把后端 VO 原样透传到展示层，按页面需要挑选与映射。
3. 数据获取：请求统一走封装的服务层（统一 base URL、错误包络、超时与取消），不在组件里散落裸 `fetch`/`axios` 调用；加载、错误、空三态显式建模；列表与表单处理竞态（去重、取消上次请求），不做「看起来能跑」的时序假设。
4. 服务端/客户端边界：默认服务端渲染或静态优先；仅在需要浏览器 API、交互状态或事件时标注客户端组件，边界标注尽量靠近叶子；不在客户端代码里内嵌密钥或仅服务端可用的凭据。
5. 状态管理：服务端数据与客户端 UI 状态分开；能靠 props、URL 或组件局部状态解决的不引入全局 store；引入状态库须说明理由并只在一处定义。
6. 错误与文案：用户可见文案走项目国际化/文案资源，不在组件里硬编码；后端错误码的文案展示与后端错误码/i18n 体系对齐，不前端另造一套语义；错误边界兜底，不白屏、不吞错。
7. 构建与环境变量：区分编译期固化与运行时注入——`NEXT_PUBLIC_*` 等前缀变量会被打进产物，不放环境差异配置、密钥或分环境 API 地址；跨环境配置走运行时注入或相对路径（与 mv-build-image-builder 的构建期固化条款同源）。
8. 安全基线：不将未消毒内容注入 `dangerouslySetInnerHTML` 等等价通道；不把密钥、内网地址、调试开关打进前端包；新依赖先过 mv-design-tech-stack-baseline 的依赖引入评估再进。
9. 样式与设计系统：样式方案（CSS Modules、Tailwind、styled 等按项目声明）同一项目不混用多套；间距、色彩走项目设计令牌，不散落魔法数值；视觉还原以设计稿为准，本规范不定义视觉风格。
10. 最小变更与测试：改动现有系统保持最小必要变更，新产生的死代码、未用 import 一律删除；业务逻辑与行为改动写或更新对应测试（组件渲染/工具函数单测），使用项目现有测试框架，不为规范而更换框架；测试分层策略与覆盖口径按项目既有约定。

## 详细参考

框架中立主体见 [references/frontend-guide.md](references/frontend-guide.md)；使用 Next.js 时并读 [references/nextjs-guide.md](references/nextjs-guide.md)。规范中的举例和阈值不应覆盖项目实际框架版本、性能特征或已确立基线。

## 输出

在交付说明中列出关键规范决策、针对本次变更的遵循/偏离原因、实际应用的框架条款、执行的验证结果；不泛泛输出整本规范。

## 自动验证与边界

优先运行项目已有检查（lint、typecheck、既有测试脚本）；没有配置的检查如实报告未执行，不虚构成功。本机把前端跑起来调试（dev server、热更新）归 mv-impl-local-debug；出包与镜像构建归 mv-build-image-builder；技术栈选型与版本基线归 mv-design-tech-stack-baseline；工程文档与图件归 mv-design-engineering-doc-writer。静态规范和自动检查不能互相替代。
