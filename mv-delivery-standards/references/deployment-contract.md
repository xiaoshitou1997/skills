# Docker 交付契约


**当前状态：dev/prod 的 deploy、rollback、status 及 target plan 均在参数校验后拒绝，不执行 SSH/SCP 或目标写入，也不产生收据。** status 原会修改权限并创建目录，故一并关闭。宿主上传覆盖共享配置，目标端锁无法保护上传；回滚历史的排序和部分记录不可靠。修复并验证这些问题后才能重新开放。独立预检会连接目标机，不代表部署可用。

以下为恢复交付前需要满足的设计与人工验证要求，不描述当前脚本能力。

## 项目输入

- `.env.dev` 和 `.env.prod` 由本地准备，**不得被 Git 跟踪**；分别包含 `APP_ENV=dev` 或 `APP_ENV=prod`，以及可选的 `HOST_PORT`、`CONTAINER_PORT` 和应用设置。不打印 env 文件内容，Java 容器通过环境变量接收配置。
- UAT、prod 等非 dev 环境按项目隔离基础设施，部署范围默认包含项目全部业务服务及其依赖的基础设施（固定版本 Tag，不用 `latest`）；多服务系统的 `compose.delivery.yml` 由项目提供。dev 环境可将开发服务器公共 infra 作为外部依赖，仅交付本项目组件；发布记录写明外部依赖、项目隔离资源及连接方式，不把共享 infra 纳入项目 Compose。所有环境的数据与凭据互相隔离。
- 用户明确说明外部依赖关系时，部署范围按声明缩减，并在发布记录注明范围与豁免项；dev 共享 infra 按上述默认执行，UAT、prod 等环境仍须满足项目隔离。交付范围仅含单服务时使用单服务模板（`templates/compose.delivery.yml`，引用 `FF_IMAGE`、没有 `build:` 段）。Node 静态前端在 env 文件中设置 `CONTAINER_PORT=80`。
- **交付上传只携带两个文件**：交付上传目标机的只有 Compose 文件与 `.env.<env>`，落 `~/.mv/delivery-standards/<app>/`；`compose.delivery.yml` 不得引用其他项目侧文件，初始化 SQL、挂载配置等配套内容随镜像打包（镜像不可变自包含），不假设目标机存在其他文件。
- **部署身份按独立生命周期划定**：独立升级、独立回滚、独立数据卷、独立端口与环境配置的一组组件是一个部署身份，对应一个 APP 名与一条完整交付链（各自的 `.env.<env>`、`compose.delivery.yml`、`releases.tsv`、收据与晋级记录）。同一系统需要多份完全独立部署（如 `order` 与 `order-sandbox`）时按多个部署身份交付，各自携带自己的基础设施容器；共享某项基础设施即不再独立，按上一条声明依赖。同一部署的横向扩容不是新身份：在同一个 Compose 项目内用 replicas 扩容，不另起部署身份。**同一个项目必须一个 stack/ns**：一个部署身份（APP）的全部组件归属同一个 stack——Compose 项目名由交付脚本固定为 `-p APP`，即 stack 名；接入 swarm/k8s 后对应一个 namespace。不把同一项目拆到多个 stack/ns，不同部署身份不共用 stack/ns（如 `order` 与 `order-sandbox` 各占一个）。APP 名在同一目标机上全局唯一——默认取模块目录名，多个项目共用目标机时 APP 名带项目前缀（如 `<项目>-<模块>`）；交付目录、stack 名、包目录与发布记录都按它区分，撞名即串栈。
- **版本与回滚历史**：恢复自动回滚前须实现完整的原子提交记录，记录实际执行顺序，并仅从已完整提交的同环境记录确定回滚目标；部分记录必须拒用。旧历史的顺序与完整性无法从文件名或 `releases.tsv` 的单行记录证明，须人工核验，不能自动选作回滚依据。这些条件尚未实现，当前回滚关闭。版本清单不能单独证明实际运行状态；恢复前还须核验镜像身份、配置和依赖状态。
- **部署流程不构建镜像**，只加载并运行不可变镜像；`docker compose` 一律 `--no-build --pull never`。
- **双探针**：可运行服务暴露 readiness 与 liveness 两个健康端点（Spring Boot 服务经 Actuator 健康组实现，条款见 mv-coding-standards 的 spring-guide「健康探测」）。liveness 只反映进程内状态、不聚合外部依赖；readiness 反映可接流状态并聚合关键依赖，是部署验证与晋级门禁的探活依据。`FF_HEALTH_URL` 指向 readiness 端点；未配置时 dev 不产生可晋级收据、prod 直接拒绝部署。
- 编排映射：收据与 prod 门禁要求 `FF_HEALTH_URL` 指向的 readiness 端点通过，且全部已发现容器运行、已配置的 HEALTHCHECK 为 healthy；未配置 HEALTHCHECK 的容器不因此被拒绝。HEALTHCHECK 属 liveness 观测，单独通过记 `liveness-only` 档、不产生可晋级收据。单个 URL 成功不证明各服务 readiness；仅声明单服务单副本且运行单容器时可记 strong；目标机须有 `python3` 解析配置，缺失或解析失败时不能记 strong，多服务或多容器 dev 记 `readiness-partial`、不产生可晋级收据，prod 验证失败。Compose 基线只有容器级 HEALTHCHECK（liveness 语义，仅标记状态、不自动重启）；镜像内 HEALTHCHECK 由模块 `Dockerfile.delivery` 声明（指向 liveness 端点，`start_period` 覆盖启动期）。swarm/k8s 接入后按 `livenessProbe`/`readinessProbe` 原生分列（失败重启/摘流），替换上述映射。

## 环境变量

环境变量（`FF_DEV_SSH`、`FF_PROD_SSH`、`FF_HEALTH_URL`、`FF_REQUIRE_DEV_PROOF`、`FF_READY_TIMEOUT` 等）的语义与默认值以 [配置参考](configuration.md) 的表格为单一事实源，本契约不再重复维护。

## 交付流程

当前所有部署和回滚入口关闭，不生成版本清单、发布记录或 dev 收据。未来恢复须解决共享配置的并发覆盖、回滚历史排序及记录完整性，并验证失败恢复。

## DEV 迁移与部署后验证

以下为交付人员按项目方案执行和记录的检查，不是脚本新增能力。按任务变更范围确定适用项；不适用须写明依据，适用项缺少条件记未执行，不得以替身结果冒充真实环境验证。

- **数据迁移**：变更涉及 schema 或数据时触发。部署前取得目标数据库及环境标识、当前与目标迁移版本、迁移文件或制品、执行顺序、旧新版本兼容性、恢复点和失败处置责任人；按项目方案确定迁移与应用切换顺序并取得所需授权。执行后核对目标版本与迁移结果，记录执行时间、目标、版本、结果及日志或记录位置。失败或版本无法确认时停止依赖该迁移的交付与验证，记录实际数据库状态、影响和处置；缺少方案、权限或目标环境时记未执行及阻塞。无数据库变更时记录不适用。部署脚本不执行迁移，容器回滚不恢复数据库。
- **运行镜像身份**：每次部署启动后，经 SSH 按服务检查实际运行容器的镜像 Image ID，与构建记录的 IMAGE_ID 和目标版本清单逐项比对；记录 APP、环境、部署版本、服务、镜像引用、期望与实际 Image ID、检查时间及证据位置。多服务时逐服务核对对应构建记录或依赖镜像身份。缺少构建身份、容器或清单，或身份不一致时记未确认或失败并排查，不以 Tag、Git SHA 或收据代替运行身份核对。
- **readiness**：部署后使用项目声明的真实 readiness 端点、目标环境和依赖，记录探测目标、时间、结果、覆盖服务、容器状态及脚本验证档位和收据位置；多服务须分别确认各服务 readiness。脚本单 URL 的结果及 strong 收据只覆盖其支持的单服务单副本单容器拓扑；partial、liveness-only 或 running-only 不证明完整 readiness。探测失败记失败，缺少端点或环境记未执行及原因。
- **冒烟**：部署后针对本次交付的关键入口和最小主路径执行项目定义的检查，输入包括访问地址、测试账号与测试数据、检查步骤和预期结果；记录环境、版本、执行时间、检查项、实际结果及日志或结果位置。失败记录现象和影响，修复后重验；缺少入口、账号、数据或环境时记未执行及原因。脚本不执行冒烟，readiness 不能替代冒烟。
- **业务验证**：任务影响业务行为时，在真实 DEV 环境按需求或验收标准选取受影响业务场景，使用真实服务及经允许的测试数据，核对业务结果和相关状态变化；记录场景、预期与实际结果、环境、版本、执行时间及证据位置。业务预期未确认时记录待确认，不编造规则；失败记录缺陷及影响，修复后重验。缺少真实依赖、数据、权限或验收标准时记未执行及原因，全 Mock 结果不能冒充真实业务验证；无业务行为影响时记录不适用及依据。脚本不执行业务验证。
- **结果交接**：汇总环境与配置检查、迁移、运行镜像身份、readiness、冒烟和业务验证各项状态及证据位置，并列出失败或未执行项的原因、影响、责任人和后续动作；不得记录凭据或敏感数据。失败或必需项未执行时如实交接阻塞，不宣称 DEV 交付验证完成。DEV 验证与收据不替代生产发布授权及原有晋级门禁。

## 身份交接与回滚证据

- 部署前取得构建记录中的 APP、完整 IMAGE、IMAGE_ID、包名与 SHA-256；经 SSH 在目标机检查 IMAGE 对应的 `docker image inspect --format '{{.Id}}'` 与构建 IMAGE_ID 一致，缺失或不一致即停止并排查。脚本接收 IMAGE 而非期望 IMAGE_ID；镜像就位检查只确认引用可解析，dev 收据不能替代与构建记录的首次比对。dev/prod 部署与回滚当前均被脚本拒绝。
- 存在已部署版本时，部署前在受控位置留存当前版本号、版本清单、Compose 文件版本或校验和、环境配置的受控版本标识及恢复位置，记录配置与旧镜像、数据库状态的兼容性验证结果；敏感值不进入发布记录。新配置覆盖目标机的 `compose.yml` 与 `.env.<env>`，版本清单只含服务、镜像引用和 Image ID，脚本不保存或恢复历史配置。缺少历史配置证据或兼容性未知时，不把镜像回退称为完整恢复；先制定并验证配置恢复方案。
- 未来恢复回滚前须确认完整提交记录及实际执行顺序，核验目标清单的 Image ID 和配置兼容性，并验证恢复后的运行状态。需要恢复配置时须先制定并验证受控方案。
- 部署或回滚失败后保留命令退出状态、时间、错误与版本证据，经 SSH 检查实际容器镜像 ID、readiness 和依赖状态，逐项与目标清单及配置证据比对。自动恢复失败、无上一版本或核验不完整时报告恢复未确认，按事故流程人工处置；`current-version` 与 `releases.tsv` 不是失败期间实际运行状态的充分证明。

## 已知限制

不内置镜像仓库、发布审批服务、产物签名、多架构分发、Helm/Kubernetes、数据库迁移或自动密钥管理。当前编排器为 Docker Compose；swarm/k8s/k3s 等编排器为后续扩展，接入时按"传输不变、apply 与回滚机制按编排器差异放 references"扩展，不改变收据与晋级门禁。收据文件不是加密签名的来源证明；团队强制测试与策略应由 CI 执行。
