# 文档类型结构

以下为默认结构，不是必须填满的空模板。不增加信息的章节直接省略；领域需要时自行增加。

## 目录

- PRD
- HLD
- LLD
- RFC / 技术提案
- API 文档
- 升级 / 部署 MOP
- Runbook
- 故障复盘（Postmortem）
- 实施计划
- 文件命名

## PRD

```markdown
# [产品 / 功能名称]

## 1. 背景
## 2. 问题陈述
## 3. 目标
## 4. 非目标
## 5. 用户与角色
## 6. 范围
### 6.1 In Scope
### 6.2 Out of Scope
## 7. 需求
## 8. 用户 / 业务流程
## 9. 验收标准
## 10. 依赖与约束
## 11. 风险
## 12. 开放问题
```

PRD 规则：

- 先陈述问题，再谈方案。
- 需求表述为可观察的行为。
- 技术选型不写入需求，除非选型本身就是约束。
- 仅当可追溯性确实有助于评审或实施时使用 `REQ-001` 类需求编号。

## HLD

```markdown
# [系统 / 功能] 高层设计

## 1. 概述
## 2. 目标与非目标
## 3. 系统上下文
## 4. 总体架构
## 5. 组件职责
## 6. 关键流程
## 7. 外部接口
## 8. 数据与状态
## 9. 部署拓扑
## 10. 非功能约束
## 11. 故障处理
## 12. 安全考量
## 13. 可观测性
## 14. 权衡与备选方案
## 15. 风险与开放问题
```

HLD 规则：

- 先定义边界与职责，再进入类/模块细节。
- 交互从文字不易看清时，使用架构图和时序图。
- 记录故障域、外部依赖和主要容量假设。

## LLD

```markdown
# [模块 / 功能] 详细设计

## 1. 概述
## 2. 范围
## 3. 模块结构
## 4. 详细流程
## 5. 接口定义
## 6. 数据模型
## 7. 状态模型
## 8. 校验规则
## 9. 错误处理
## 10. 并发、幂等与重试
## 11. 配置
## 12. 日志、指标与追踪
## 13. 安全控制
## 14. 测试设计
## 15. 部署 / 兼容性说明
## 16. 开放问题
```

LLD 规则：

- 输入与读取顺序：先读用户任务、已确认的需求与验收标准，再读适用的 HLD、架构决策及项目约束，再查现有代码、接口、数据结构、配置与测试，最后核对相关依赖契约和运行资料。不存在的输入标明缺口；输入之间有冲突时记录双方及来源，不自行裁决。
- 产出位置：优先更新项目已有的详细设计文档及其约定位置；没有既有位置时遵循项目文档目录约定，再按本文「文件命名」默认规则落盘。局部修订沿用现有结构，只修改任务范围及直接受影响的内容。
- 按业务或系统流程组织设计：对每个涉及的流程写明触发条件、输入、参与模块及职责、处理步骤与顺序、分支和状态变化、输出或副作用；列出边界、失败路径及其处理。跨组件顺序不易看清时补充时序图，图与正文使用相同术语。
- 接口：涉及模块间、外部接口或事件时，说明调用方和提供方、请求与响应或消息字段、校验、认证授权及兼容性；字段、错误码和契约仅按已有来源或已确认决策填写。
- 数据与状态：涉及持久化、数据变更或状态迁移时，说明数据项及约束、读写归属、迁移条件和结果；涉及事务时说明事务边界及失败后的数据状态。
- 错误处理：对输入无效、依赖失败和业务拒绝等实际存在的路径，说明触发条件、对调用方的结果、记录和恢复方式；来源未定义的行为列为待决。
- 并发、幂等与重试：存在并发写入、重复请求、消息重复投递或重试时，说明冲突场景、预期结果与已确认的控制方式；不适用时说明原因，不为填章节虚构机制。
- 追溯与验收：逐项关联本次范围内的需求或验收条目、对应设计流程或规则、测试场景及预期结果；沿用已有标识，没有标识时引用可定位的条目。验收描述给出前置条件、操作或输入、可观察结果及可判定的通过条件；未确认的阈值不自行设定。
- 未决与就绪：逐项列出缺失输入、假设和开放问题，说明影响的流程或需求、阻塞的实施或测试工作、待确认事项及已有责任人；未指定责任人时标记待定。存在阻塞实施或验证的未决项时标记「未就绪」，并写明解除条件；阻塞项均已解决且追溯和验收可验证时才标记「就绪」。未就绪仍可交付标明状态的草稿。
- 提供了代码、表结构、API、配置时，命名与实际保持一致；不把现状推断成已批准的新设计。

### LLD 写法示例

以下仅示范表达粒度，不作为项目业务规则。

| 项目 | 示例 |
| --- | --- |
| 需求与验收 | `REQ-1`：仅待处理记录可被取消；取消后不可再次取消 |
| 触发与输入 | 已登录用户调用取消接口，提供记录 ID |
| 校验与授权 | 服务端校验 ID 格式、用户权限和记录归属；不满足时拒绝且不修改数据 |
| 流程与事务 | 在一个数据库事务内按 ID、归属和待处理状态条件更新为已取消；更新行数为 1 时返回成功，提交后记录审计事件 |
| 分支与并发 | 记录不存在或不属于用户时返回项目约定的不可访问结果；记录状态不允许取消或并发更新行数为 0 时返回项目约定的状态冲突结果；不得报告取消成功 |
| 验证 | 待处理且有权限时返回成功且状态变为已取消；无权限时返回拒绝且状态不变；已取消时返回状态冲突；两个并发取消请求仅一个返回成功、另一个返回状态冲突，最终状态为已取消；用集成测试核对响应和数据库结果 |

错误码、审计事件持久化及提交后的失败处理应按项目已确认契约补充；未确认时标为待决，不从示例推断。

## RFC / 技术提案

```markdown
# RFC: [标题]

## 摘要
## 1. 背景与问题
## 2. 目标
## 3. 非目标
## 4. 约束
## 5. 方案
## 6. 详细设计
## 7. 兼容性与迁移
## 8. 已考虑的备选方案
## 9. 决策
## 10. 理由
## 11. 影响与权衡
## 12. 风险
## 13. 上线 / 回滚
## 14. 开放问题
```

RFC 规则：

- 设计类 RFC 必须收敛到决策。
- 决策未定时写 `Decision: TBD`，并列出阻塞问题。
- 不把多个选项并列呈现，仿佛“选择”不属于本文档的任务。

## API 文档

```markdown
# [API 名称]

## 1. 概述
## 2. 端点 / RPC
## 3. 认证与授权
## 4. 请求
### 4.1 Headers / 元数据
### 4.2 路径 / 查询参数
### 4.3 Body / 消息结构
## 5. 响应
### 5.1 成功响应
### 5.2 错误响应
## 6. 校验规则
## 7. 幂等与重试
## 8. 示例
## 9. 兼容性与版本
## 10. 运维注意事项
```

API 规则：

- 字段用表格：名称、类型、必填、约束、说明。
- 名称与大小写严格对齐来源规格或代码。
- 不虚构字段、默认值、错误码或认证方式。
- 异步 API 在已知时补充回调/事件关联与重试行为。

## 升级 / 部署 MOP

```markdown
# [系统] [版本] 升级 MOP

## 1. 变更概述
## 2. 范围与影响
## 3. 前置条件
## 4. 所需权限与物料
## 5. 备份与恢复准备
## 6. 执行步骤
## 7. 检查点与验证
## 8. 回滚触发条件
## 9. 回滚步骤
## 10. 变更后验证
## 11. 已知风险
## 12. 联系人 / 责任人
```

MOP 规则：

- 起草前先读 `mop-guide.md`。
- 命令保持可复制、有序。
- 风险高或不可逆的步骤之后应紧跟验证。
- 回滚路径未真正定义时，不得声称可以回滚。

## Runbook

按用途、触发条件/告警、诊断、决策树、处置、验证、升级上报和恢复组织章节。例行操作与紧急操作分开。

## 故障复盘（Postmortem）

按摘要、影响、时间线、发现、根因、促成因素、响应、恢复、经验教训、整改动作和证据组织章节。无证据时不归因动机或指名责任。

## 实施计划

当任务包含多个相互依赖的工作项、跨模块交付、迁移或分阶段实施时编制计划；单一且可直接验证的小改动可用简短步骤代替完整计划，并说明裁剪范围。沿用项目已有计划或工单，不强制新建平行台账。

先读取任务目标、范围、已确认需求与验收、适用设计和架构决策、现有代码及依赖约束；缺失或冲突的输入列为开放问题，不虚构日期和责任人。

1. 按可独立交付或验证的业务结果分解工作，覆盖适用的设计、实现、迁移、测试、交付与回滚；每项写明范围、输入、产出、验收条件及验证方式。
2. 标识工作项间的前置依赖、外部条件和阻塞关系，按依赖排序；需要分阶段交付时记录里程碑及其完成条件，不将未确认排期写成承诺。
3. 将需求和设计映射到工作项及验收，核对遗漏、重复和跨项接口；记录风险、假设、未决事项、影响范围与解除条件。
4. 当前工作项的关键业务规则或验收未决时，只阻塞依赖该决策的设计、实现或验证，继续可独立开展的工作；决策确认或输入变化后更新受影响的任务、依赖和验收。

按目标、范围、工作分解、依赖、里程碑、迁移、测试计划、上线、回滚、风险和开放问题组织章节；无关章节省略。

## 文件命名

优先小写加连字符：

- `prd-<功能>.md`
- `hld-<系统>.md`
- `lld-<模块>.md`
- `rfc-<主题>.md`
- `api-<服务>.md`
- `mop-<系统>-<版本>.md`

保留单一权威版本，不使用 `final-v2-latest` 式后缀。

落盘默认仓库 `docs/` 平铺（命名公式已含类型前缀，不另设类型子目录）；成套多文件产物落专目录（目录名按该文档集的用途命名）。项目已有文档目录约定优先。
