# 仓库布局与基础设施拓扑

mv 团队项目仓库布局默认形态与共享契约约定；配合本 skill「新项目初始化」判据使用。既有项目以实际布局为准。

## 单仓多模块布局

默认目录形态（端按项目需要裁剪；目录名即模块名，后缀取闭集）：

```text
<project>/
├── pom.xml                  根父 POM：聚合后端模块，项目名 = 仓库根目录名
├── <project>-common/        共享设施：异常、常量、工具（不带端词）
├── <project>-service/       可运行入口：controller/admin/ 与 controller/uc/ 分包
├── <project>-entity/        可选：第二个可运行消费者出现才拆，默认并入 service 分包
├── <project>-web/           用户端网页（含按需 Portal）与运营管理后台共用的前端工程
├── <project>-user-mp/       用户端 Taro H5/小程序（按需，一工程双编译目标）
├── .env.example             环境变量样例（占位值）
└── .github/workflows/       CI 样例
```

- 目录名即模块名逐字相同（Maven artifactId、npm name 均取目录名），后缀闭集与切片词规则见 mv-coding-standards 模块命名条款。
- 前端工程不进后端聚合 pom；后端模块不引用前端目录。
- 多仓拆分判据见正文「仓库布局判据」；跨项目集成时按消费者需要拆 api 模块并发包共享，不复制 DTO 源码。

### C 端双端产品默认形态

```text
<project>/
├── <project>-user-service/    用户端后端入口
├── <project>-admin-service/   管理端后端入口
├── <project>-entity/          两入口共用的业务实现与数据访问
├── <project>-user-web/        用户端网页（公开网站与按需 Portal）
├── <project>-admin-web/       运营管理后台界面
└── <project>-user-mp/         用户 H5/小程序（按需）
```

用户端公开网站与 Portal 可共用 `-user-web`，按路由、布局及权限区分；有独立发布或技术需求时可分别建立前端工程。`-user-service` 服务用户网站、Portal、小程序和 App，`-admin-service` 服务运营管理后台；后台指界面，后端入口指服务。每个入口及前端工程独立构建和部署，分别配置认证、授权、探针和发布回滚；业务规则与数据由同一个实体模块负责，不按端复制。两个进程共用实体库和数据库时，并发约束依靠数据库事务、约束或锁，不能依靠进程内锁；数据库迁移须兼容两端的独立发布。分离入口不要求拆分域服务；仅有小程序时不创建用户端网页。现有 mv-delivery-standards 契约要求同项目一个 stack，且多服务 Compose 不能完成生产晋级；项目交付方案须明确这一限制和可用交付方式，不能声称当前脚本已支持该拓扑。

### 双端微服务完整形态

用户端 + 管理端 + 多域微服务的完整形态（域按业务裁剪）：

```text
<project>/
├── <project>-user-service/      接入层：用户端入口，聚合各域服务
├── <project>-admin-service/     接入层：管理端入口
├── <project>-task-service/      定时任务与消息消费进程
├── <project>-order-service/     服务层：订单域微服务
├── <project>-member-service/    服务层：会员域微服务
├── <project>-product-service/   服务层：商品域微服务
├── <project>-order-entity/      仅跨服务共享实现的域才拆
├── <project>-common/  <project>-user-api/  <project>-admin-api/
├── <project>-user-web/          用户端网页（shadcn-admin + Vite + React + TypeScript）
├── <project>-user-mp/           用户端小程序 + 移动端 H5（Taro 一工程双目标）
├── <project>-user-mobile/       用户端 App 壳（按需加载 Taro H5，原生能力按项目确认）
├── <project>-admin-web/         管理端（shadcn-admin 衍生）
└── .env.example  .github/workflows/
```

接入层（端词切片的入口）与域服务层（域词切片）是两个功能层级：端入口聚合域服务、对外提供 `/uc` 与 `/admin` 契约，域服务不对公网暴露；两者共存不构成「同一层级混用按端切与按域切」。归属单一端的模块带端词切片：网页走 `-user-web`，移动端 H5 与小程序是 `-user-mp` 的两个编译目标（一份代码两个部署物），App 壳按需使用 `-user-mobile` 并加载 Taro H5，壳与原生能力方案按项目确认；契约模块按端拆 `-user-api`/`-admin-api`（有外部集成的端才建）；`-common` 为跨端共享设施，不带端词。

## 共享契约与类型同步

- 契约真源是后端：接口经 springdoc/OpenAPI 暴露（`springdoc-openapi` starter，`/v3/api-docs`），接口文档与契约同源生成，不手写第二份。
- 前端类型来源二选一并全项目一致：经 OpenAPI 生成器从 `/v3/api-docs` 生成 TS 类型，或依据后端接口契约集中映射（`types/api` 集中定义）；不散落各页面重复声明，也不强制创建 api 模块。
- 后端字段变更同步前端类型的责任在变更方：契约变更交付说明或 PR 描述列出受影响端，前端类型与映射层在同一变更内更新。

## dev 公共 infra

- 本地业务进程在宿主前台直启，默认连接经 SSH 管理的 dev 公共 infra；部署到开发服务器的 dev 应用也可接入同一公共 infra；不在宿主安装或运行 Docker。PostgreSQL、Redis、RabbitMQ、RustFS、SFTPGo 按项目实际需要接入，不为每个项目重复创建基础设施栈；公共服务使用固定版本，由维护方统一管理升级、容量、备份和故障通告。
- 各项目使用独立身份与授权：PostgreSQL 使用独立数据库或 schema 及账户；Redis 使用项目键前缀和受限 ACL，限制键与频道范围并禁止全局清理及管理命令；RabbitMQ 使用独立 vhost 与账户；RustFS 使用独立 bucket 与最小权限凭据；SFTPGo 使用独立账户、根目录及权限。不能实施权限隔离的共享服务不得用于该项目，改用隔离实例；使用不属于自己的资源的请求须被拒绝。
- **信息交接**：需要公共 infra 时执行下方「本机公共 infra 配置产物」的读取、确认、维护和验证流程。用户可预填；已有信息直接复用，仅询问本次缺项，不主动联系他人。项目文档保留非敏感接入说明；真实凭据由用户配置到未跟踪的本地环境文件、进程环境或项目密钥管理系统，不要求在对话中发送密码，不打印或提交凭据。
- README 或开发环境文档记录所需服务、服务器别名、非敏感地址和端口、项目资源标识、申请方式、授权范围、环境变量键、连接检查、不可用时行为与责任人；`.env.example` 只含占位值。经受控网络或 SSH 隧道连接，不得使用生产凭据、生产数据或跨环境连接。
- 依赖按功能接入：纯逻辑开发可关闭当前不需要的功能或使用明确标识的本地替身；已关闭功能被调用时返回可理解的不可用结果，不伪报成功。核心依赖缺失时启动失败或 readiness 不通过；缓存、消息和文件服务仅在业务允许且已实现安全降级时可缺失启动，记录受影响功能。
- `compose.dev.yml` 不用于重复部署公共 infra；业务服务默认不进入开发编排。项目文档化开发拓扑为容器时按 mv-delivery-standards 的 dev 交付执行，dev 项目部署可将公共 infra 作为外部依赖，UAT、prod 等环境不跨项目共享基础设施；各环境的地址、凭据及数据保持隔离。

### 本机公共 infra 配置产物

此文件是本 skill 拥有和维护的用户本机配置产物，供后端、测试等 skill 读取；跨 skill 调用本 skill 并按本节执行维护，不直接写入其私有状态目录。文件不属于项目仓库，不提交或复制到项目；用户可自行预填和修改。

- 路径：默认 `~/.mv/design-standards/dev-infra.json`；设置非空 `MV_DESIGN_STANDARDS_HOME` 时为该目录下的 `dev-infra.json`。`~` 指执行 agent 的宿主用户目录：Windows 使用 `USERPROFILE`，macOS/Linux 使用 `HOME`；覆盖值为宿主绝对路径，按宿主文件系统解析，不按 SSH 目标机解析。空覆盖值视为未设置，目录不存在时仅在写入时创建。
- 格式为 UTF-8 JSON 对象，`schemaVersion` 为数字 1；`services` 和 `projects` 为对象，可为空。以下仅示意字段形状，省略未确认字段，不把占位值当作可用信息：

```json
{
  "schemaVersion": 1,
  "services": {
    "<service-id>": {
      "type": "postgresql|redis|rabbitmq|rustfs|sftpgo",
      "environment": "dev",
      "connection": {
        "mode": "direct|ssh-tunnel",
        "host": "<服务目标主机>", "port": 1,
        "sshAlias": "<宿主 SSH 别名>",
        "localHost": "<隧道监听地址>", "localPort": 1
      }
    }
  },
  "projects": {
    "<用户确认的项目标识>": {
      "repositoryRoots": ["<宿主仓库根目录绝对路径>"],
      "dev": {"<service-id>": {"resource": "<资源标识>", "identity": "<账户标识>", "credentialRef": "<凭据引用>"}},
      "test": {"<service-id>": {"resource": "<测试资源标识>", "identity": "<测试账户标识>", "credentialRef": "<测试凭据引用>"}}
    }
  }
}
```

- `service-id` 是文件内稳定的公共服务标识，同类多实例用不同 ID；`type`、`mode` 分别取示例中一个枚举值，端口为 1–65535 的整数。`host`/`port` 是直连目标；隧道模式下是从 SSH 目标机可达的远端转发目标，另需 `sshAlias`、`localHost`、`localPort`，应用连接本地监听端点。直连不需要隧道字段；别名由宿主 SSH 配置解析，隧道端口冲突时询问可用端口并更新确认值，不猜地址或账号。记录隧道生命周期与连接检查结果。
- `projects` 键是用户确认的稳定项目标识，不从目录名猜测；`repositoryRoots` 是该项目在宿主的仓库根目录绝对路径字符串数组，可含多个检出目录。每个环境以服务 ID 引用 `services`。`resource` 写数据库/schema、Redis 键及频道前缀、RabbitMQ vhost、bucket 或 SFTP 根目录等实际隔离标识；需要多项时用非敏感字符串明确列出。`identity` 是非秘密账户标识，`credentialRef` 只写环境变量名、密钥管理系统引用或本地未跟踪文件的路径及键名，绝不写密码、令牌、私钥或含密钥的连接串。不得将凭据值写入该产物、日志或项目文档。
- `dev` 与 `test` 使用独立资源、身份、凭据及数据；可引用同一个公共服务 ID，但仅当服务能实施资源和权限隔离。无法隔离时使用另一个专供测试的服务 ID；全局配置或管理命令测试必须用独立测试实例。仅允许 dev 公共服务及其隔离测试资源，禁止记录或连接生产目标、凭据和数据。

**读取与维护流程**：

1. 根据本次任务确定环境和所需服务；先读取用户本轮明确提供的信息，再直接读取该文件，再核对项目 README、开发环境文档、已有配置和 `.env.example`。用当前工作目录所属 Git 仓库的实际根目录匹配各项目 `repositoryRoots`：两侧均解析绝对路径、符号链接和路径分隔符，Windows 按不区分大小写比较，其他宿主按区分大小写比较；仅精确匹配，唯一命中直接采用项目标识，无命中或多项目命中才询问用户。非 Git 工作目录询问仓库根目录与项目标识，不以目录名猜测。用户确认后将当前根目录合并写入对应项目的 `repositoryRoots`，已有其他路径保留；显式指定项目与路径匹配结果冲突时按冲突处理。只检查本次所需字段和引用；空值、占位值、缺字段均视为缺项。与文件或项目资料不一致时列出冲突并请用户确定最终值，未确认前不连接或覆盖冲突项。
2. 文件不存在时按空对象处理；无论文件是否存在，都只询问本次所需且尚未确认的项目标识、服务、端点、资源、身份、凭据引用与连接方式，不索要凭据值。用户确认后由本 skill 将非秘密信息合并写回固定文件，保留其他项目、服务和未知字段；尚未确认的字段保持缺省。用户拒绝提供或凭据尚未配置时报告阻塞，只继续不依赖这些信息的工作。
3. JSON 无法解析、根对象或已用字段类型错误、版本未知、服务引用不存在或内容包含秘密时停止使用受影响配置，不覆盖原文件；报告具体问题并请用户修复或确认处理方式。隔离配置不满足时停止相关测试并报告，不复用开发数据或凭据。写入前须原子创建同目录的 dev-infra.lock 目录作为协作锁；已存在时停止更新，不按年龄自动删除。获取锁后在锁目录写入随机令牌、主机、进程标识和获取时间，持锁期间重新读取并合并其他项目、服务和未知字段；冲突无法裁定时停止并报告。操作结束后核对锁内令牌再释放，释放失败时报告遗留锁及是否已发布；遗留锁先确认持有者已停止；锁内身份缺失或无法确认时不解除并报告，需由用户核查所有可能写入者已停止后处理。锁只约束遵循本协议的会话；用户及其他程序编辑前须停止遵循本协议的写入，agent 更新期间须停止其他程序编辑，无法确认时不写入。发布前再次核对原文件内容摘要；首次创建以文件不存在为基线，发布前确认仍不存在；状态变化则停止；摘要检查无法消除检查后外部写入的竞争。文件系统不支持原子创建目录或原子替换时不写入。发布前失败时保留原文件并报告未发布；发布后清理失败时报告已发布及遗留问题，不声称原文件未变。
4. 写入仅限已确认的非秘密字段，创建时包含版本和两个空对象；先写同目录临时文件，校验 JSON 后原子替换，限制文件及目录访问权限为当前用户可读写，宿主不支持该权限模型时报告实际权限。不得用新文件覆盖损坏原件或清空未涉及信息。
5. 使用前检查凭据引用是否已配置，以不输出密钥的方式验证目标服务、项目资源及最小权限；记录环境、服务、实际连接端点、资源、隔离方式、结果及失败原因。缺少配置、授权不足、隧道或服务不可达时报告具体阻塞项，不猜测、不接生产、不擅自另建基础设施；测试未执行不得报通过。

## CI 样例

- 最小门禁：PR 触发「后端编译 + 单测」「各端 lint + typecheck + 单测」两条 job，样例用 GitHub Actions，只为已存在的后端或前端模块建立对应 job；跑不通的流水线不入主干。
- 交付类检查（镜像构建、部署）不在 CI 样例内，归 mv-delivery-standards 的交付流程。

本文只定仓库布局与本地拓扑；后端模块命名细则归 mv-coding-standards，交付编排与部署归 mv-delivery-standards。
