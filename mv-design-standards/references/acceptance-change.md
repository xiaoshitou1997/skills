# 验收与需求变更

适用于功能验收定义与已确认需求的变更评审。验收依据以项目确认记录为准；本文件不替代测试执行、业务验收或上线审批。

## 验收标准

每条独立需求至少有一个可验证标准，采用项目已有格式或「前置条件 / 输入与动作 / 预期结果 / 证据」描述；不强制使用特定测试语法。

1. 主路径验证业务结果、持久化状态与对外可见行为，而非只验证 UI、HTTP 状态或日志出现。
2. 有边界的规则覆盖边界内、边界上与边界外；金额与数量写清单位和精度，时间写清时区与边界包含关系。
3. 有权限或数据隔离的功能覆盖允许与拒绝、本人和非本人范围；角色及租户模型以项目已确认需求为准。
4. 有异步或外部依赖的功能覆盖处理中、失败、重复与恢复后的结果，区分同步受理成功与最终业务成功。
5. 性能目标包含场景、数据量、负载、环境、观察窗口和阈值；阈值无来源时列待确认，不套用其他项目的 P95、QPS 或并发数。
6. 证据写明取得方式与判定对象；尚未执行的验收不记为通过，需求草稿不冒充确认版本。

## 需求到验证的追溯

沿用项目工单或需求编号建立轻量映射：需求 → 关键规则 → 验收标准 → 对应测试或人工证据。测试实现与分层归 mv-coding-standards，正式 PRD 的章节组织见本 skill「工程文档与图件」；不在多个文档维护独立需求真源。

## 需求变更评审

1. 记录变更来源、原约定、新约定与业务原因；未确认的新想法标为提议。
2. 沿业务流程核对影响：角色与数据权限、规则和状态、上下游契约、存量数据、已完成工作、测试与交付范围。
3. 对已上线行为确认兼容窗口、存量数据处理、用户可见差异与回退限制；技术实现及迁移方案交对应规范评估。
4. 列出需要重新确认的验收与责任角色；范围、时间或成本影响尚未确认时如实记录，不自行承诺交付日期。
5. 确认后同步需求真源、受影响规则与验收，通知或平台写入仅在授权范围内执行；未受影响的条目不重复改写。

## 交接就绪

独立工作项能够进入实现的判据：目标与范围可说明、关键规则无阻塞冲突、验收可观察、关键依赖及未决项可识别。局部未知只阻塞相关分支，已明确且独立的工作继续推进。

本文只规定验收口径与变更分析；测试通过、业务确认和生产发布分别由对应流程留证。
