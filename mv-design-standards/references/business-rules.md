# 业务规则与流程

适用于业务访谈、功能分析与规则评审。业务事实取自当前项目来源；示例只演示描述方法，不作为通用规则。

## 从目标建立业务模型

新系统或跨流程变更按以下步骤分析完整生命周期；局部变更只分析受影响的角色、旅程、状态与相邻交接，记录未覆盖范围。使用现有需求、工单或文档承载结果，不强制新建文件或重复编号。

1. 从业务目标及成功判据列出业务概览，识别为达成目标需要参与的人员、组织和外部系统，记录各自目标与职责；候选角色保留来源和确认状态。
2. 按角色目标梳理从触发到业务结果的旅程，列出步骤、交接、信息及业务能力；从创建、使用、变更到结束或退出检查相关业务对象的生命周期，不适用的阶段说明原因。
3. 将旅程中的能力整理为业务能力清单，以角色达成的业务结果为单位建立用例目录；每项记录目标、参与者、触发条件、前置条件、结果及其来源。相同业务结果复用已有条目，不按页面或接口机械拆分。
4. 对本次范围内的用例描述主流程、备选与异常路径、业务规则、状态变化和人工介入；关联对应需求与可观察验收，缺少依据的行为列为待确认。
5. 建立轻量覆盖映射：目标 → 角色与旅程 → 能力及用例 → 生命周期状态和规则 → 需求与验收。逐项检查无用例支撑的目标、无归属的角色交接、缺失的状态或异常路径，以及无验收的需求；记录缺口、范围外项与处理状态，不以条目数量宣称完整。

## 事实与确认状态

- 已确认（CONFIRMED）：有项目来源及有权角色确认的业务要求，记录来源、确认人或确认记录。
- 推断（INFERRED）：从资料、现状或上下文推导的候选结论，记录依据和待核实对象；现状事实本身与推导出的需求分开。
- 假设（ASSUMPTION）：为继续分析或独立工作暂定的前提，记录理由、影响及验证方式，不作为已批准规则实现。
- 待确认（OPEN）：缺失、冲突或需要业务决策的问题，记录问题、来源、影响范围、待确认角色与解除条件；未指定角色时标待定。

状态可随确认更新；推断和假设需要确认时关联待确认问题，不因模型或文档完整而自动升级为已确认。

## 术语与角色

- 术语表只收录容易混淆或影响接口、计算与验收的概念：术语、定义、来源、同义词及字段映射。
- 角色按业务职责定义，区分操作者、审批者、数据所属方与系统身份；同一人可具有多个角色，但权限与数据范围分别确认。
- 未确认的行业缩略语保留原文并标注待确认，不按字面推断其业务含义。

## 业务规则

每条规则写成「前置条件 → 判断 → 结果」，按需求记录适用对象、数据来源、例外与失败行为。规则涉及以下内容时补齐判据：

| 类型 | 必要判据 |
| --- | --- |
| 计算 | 单位、精度、舍入时点、汇总次序、空值与负值行为 |
| 时间 | 业务时区、日历日或工作日、截止边界、超时处理 |
| 权限 | 谁对哪些数据执行何种动作、越权结果、审计需求 |
| 唯一与重复 | 唯一范围、重复请求或重复事件的业务结果 |
| 状态 | 合法迁移、前置状态、触发角色、终态与撤销条件 |
| 外部交互 | 对端责任、超时、重复或乱序消息、人工核对与补偿结果 |
| 数据生命周期 | 来源、修改权、留存依据、归档与删除结果 |

实现机制（锁、事务、消息队列等）由架构与编码规范决定，不在业务规则中提前指定，除非项目已有明确约束。

## 流程与状态

1. 主流程写清触发者、前置条件、步骤、分支与业务完成条件。
2. 补齐相关异常：输入无效、权限不足、外部超时、重复提交、处理中断、人工撤销；无关情形不强加。
3. 有状态对象采用状态表：当前状态、事件、条件、下一状态、副作用、失败后的可观察结果。未定义迁移不自行补为允许。
4. 跨系统流程明确各方完成标准与最终业务结论；是否采用重试、补偿或人工对账由后续设计落实。

## 描述示例

- 场馆预约：「相同资源、相同时间范围的重复申请如何判定冲突」需要确认区间边界和处理中的占用策略，不能套用电商库存规则。
- 检验报告：「报告签发后能否更正」需要确认授权角色、版本保留和已分发副本处理，不能默认允许原记录覆盖。
- 设备告警：「重复上报是否生成新告警」需要确认事件标识、合并窗口与恢复条件；窗口长度由项目确认。

本文件只规定规则的分析与表达；行业口径由业务方确认，技术方案由本 skill「架构与选型」与实现规范承接。
