# 需求与方案设计

面向 MV 团队自研系统的需求分析、架构决策、技术栈基线、工程文档与图件、新项目初始化：把从业务约定到可运行骨架的设计过程落成可验证的产物。业务编码与测试写法、镜像构建与容器部署不归本 skill。

## 作用与优先级

本 skill 覆盖 design 阶段四个子领域：需求分析、架构与选型、工程文档与图件、新项目初始化。优先级：用户明确需求和项目已确认约定 / ADR → 本规范 → 模板与生态默认；来源冲突显式列出，不将旧项目规则、通用行业经验或当前代码行为自动视为新需求。

需求分析按变更规模裁剪：小变更补受影响的规则和验收即可，新系统或跨流程变更再建立完整上下文。架构决策先于实现：涉及跨模块、跨服务、跨团队、数据隔离或不可逆迁移的决策先写 ADR 再开工，能在单模块内解决的不上升为系统级决策。既有项目技术差异不自动触发改造，升级是独立决策。初始化只执行已确认范围，不默认全量端全量设施。

## 脚本位置

`SKILL_ROOT` 必须显式设为本次加载的 skill 目录，不能假设环境已提供；脚本路径恒加引号。命令从用户项目目录执行，不在 skill 目录内产生运行时文件。

## 需求分析

面向各项目的需求分析与变更评审，产出可实现、可验证的业务约定。行业规则以当前项目的来源与确认记录为准；正式文档的结构与图件见「工程文档与图件」，技术架构与服务边界决策见「架构与选型」。

### 工作流程

1. 确定当前项目与任务范围：新建、存量接管、新功能或需求变更；按 [项目上下文](references/project-context.md) 读取现有项目资料，记录本次涉及的角色、系统、数据和约束。团队技术栈为默认方案，项目选型偏离按「架构与选型」的技术栈基线处理。
2. 整理来源与状态：按 [业务规则](references/business-rules.md) 区分已确认、推断、假设与待确认，记录依据、影响及确认人或待确认角色。现有代码只能证明当前实现，不能单独证明客户要求。
3. 定义目标与范围：写清业务问题、可观察的成功判据、本期交付与排除项；列出业务方、使用方、验收方和外部系统责任边界。缺少具体人名时记待指定角色，不编造责任人。
4. 建立业务模型：按 [业务规则](references/business-rules.md) 从目标识别角色、旅程、能力、生命周期和业务用例，分析主流程、备选与异常路径并检查覆盖；候选角色与能力标明推断或待确认，不预设行业模型。
5. 定义验收：按 [验收与变更](references/acceptance-change.md) 将每条独立需求映射到输入、动作、可观察结果与证据；功能、安全、性能和恢复目标按实际风险补充。数值阈值需有来源或显式标为待确认。
6. 处理未决项：区分阻塞实现的业务决策与可继续的独立工作；金额计算、授权范围、状态终态等未决时先保留接口或草稿，不编造规则实现。非阻塞信息先标注并继续，不重复索取资料已有的答案。
7. 评审与交接：记录范围、规则、验收及未决项的确认状态；按影响转交架构、编码、安全与测试规范。需要正式 PRD、流程图或评审稿时按「工程文档与图件」节执行；只要求梳理需求时直接交付分析结果。

产出按任务规模裁剪：业务概览、领域术语、能力与用例目录、旅程和生命周期、覆盖分析、需求条目、业务规则、验收标准、来源与确认状态、假设与开放问题；变更任务追加影响范围和需要重新确认的验收项。沿用项目已有编号或工单标识，只为可独立交付或验收的需求新增标识，不另造平行台账。

## 架构与选型

面向自研系统的架构决策与评审：定系统边界、依赖方向、一致性与集成方式，并把决策落成可执行的 ADR 与评审记录；同时维护团队技术栈基线，约束选型、基线维护与依赖演进决策。本节不负责接口字段设计、编码实现与部署；安全政策、数据分级与供应链处置归 mv-security-standards。

### 开始前确认

开始前核对：业务目标与核心用例、预期规模（用户量、数据量、峰值）、可用性与恢复目标（RTO/RPO）、合规与数据敏感级别、团队规模与发布节奏、既有系统与外部集成边界。当前工作项的关键业务规则、验收或方案有歧义时列出来源和影响并询问有权确认的角色；仅暂停依赖该决策的设计与实现，继续不依赖它的工作。其他未知记录假设及验证方式，不默认微服务、多租户或消息队列。

### 术语

用户后台（Portal，如个人中心、客户工作台）和运营管理后台均为人员操作的前端界面，分别属于用户端和管理端；后端是提供接口、执行业务规则及访问数据的服务。讨论架构与交付时写明「用户后台」「运营管理后台」「用户端后端」或「管理端后端」，不以「后台」代称后端。后台任务、后台作业指非前台运行的任务，不属于上述界面术语。

### 关键规则

1. **默认形态按产品选择**：多数同时有管理端和用户端的项目，默认单仓、共用 `<project>-service` 与 `<project>-web`；面向 C 端消费者且同时有两端的产品，默认用户端和管理端的前端工程、后端入口及部署单元分离。仅有一个端时只建实际需要的端。两种形态均使用团队技术栈。
2. **例外与进一步拆分**：其他项目出现独立团队、独立发布、伸缩、网络或数据合规边界时可按端拆分；C 端产品若两端实际共用发布与部署，且项目明确接受共用入口的影响，可记录理由后共用。按业务域拆服务还须评估数据所有权、分布式事务、网络故障与运维成本；端入口分离不等于必须拆分域服务。
3. **身份域按用户人群划分**：多用户系统的 IdP 选型是设计前置，认证方案设计前确认承载 IdP（企业既有 IdP、团队统一 IdP 或项目自建 Keycloak 等），未确认不开建用户认证。管理端用户与用户端用户分属不同人群（如内部员工与外部消费者）时默认分域承载：管理端接企业既有 IdP 或独立 realm，用户端走独立消费者身份域，各端登录页只接本域入口；同一人群合一个身份域。OIDC client 按登录入口注册：单入口单服务一个 client，管理能力与业务能力由 RBAC 角色区分（如 MeterSphere 型测试平台）；按端分离的每个入口各自注册 client，按 scope 区分授权边界。客户端隔离与会话互不互认的实现条款见 mv-coding-standards spring-guide「认证配置」。
4. **边界与数据所有权**：每个业务能力及数据有唯一所有者，用户端和管理端调用同一权威业务实现，不按端复制业务规则或各自维护同一份数据。独立域服务跨边界只经接口或事件，不直接读对方表；两个入口共用同一实体模块时由该模块统一管理数据访问。公共设施放 common，跨项目契约按需放 api 模块。
5. **依赖方向单向**：接入层 → Service 层 → 基础设施；Service 层不反向依赖接入层，不依赖具体框架的 Web 组件；跨层调用与循环依赖视为架构缺陷。
6. **同步默认，异步按需**：请求-响应能表达且满足需求时延要求时用同步；出现解耦、削峰、跨团队异步或长流程四类诉求之一才引入消息队列。异步链路必须设计幂等、重试、死信与可观测性。
7. **一致性显式化**：单库本地事务优先；跨服务一致性用 Outbox、Saga 或对账，不默认引入分布式事务；写明业务可接受的延迟与失败补偿方式。
8. **外部集成走防腐层**：第三方 SDK、协议与数据模型不直接渗透到 Service 层；在边界处转换成本方模型，统一超时、重试、熔断、限流与验签。
9. **多租户默认关闭**：确有多个客户共享一套部署时，按合规与规模选择隔离模型（独立库、独立 schema、共享表 tenant_id）；所有查询强制租户过滤，唯一约束含租户，跨租户管理走单独授权。
10. **非功能约束进设计**：容量、可用性、恢复目标、可观测性、成本与数据保留在方案阶段明确；关键指标不能等到运维阶段补。
11. **演进可回退**：接口与数据结构按 expand–contract 演进，先兼容后收紧；大改拆分批次，每批可独立发布与回滚；不一次性大爆炸重构。
12. **决策留痕**：影响面跨模块、不可逆或存在多个可行备选的决策写 ADR；ADR 记录背景、决策、备选、影响与回滚，不记录讨论过程。
13. **评审看失败模式**：架构评审不只画组件图，逐项检查边界是否清楚、依赖是否单向、数据是否归属明确、失败与重试是否可收敛、权限与租户是否隔离、观测与回滚是否具备。
14. **值域形态按扩展驱动方定**：值域由谁驱动扩展决定存储形态——用户操作即可新增值（数据驱动）建真表加真外键；新增值必须发版（代码驱动）用枚举。判定三问：新增一个值需不需要改代码（新平台要写适配器即需要）；一行只插入、无代码配合能否干活（死行为不能，插入即生效为能）；行有没有自身属性要挂（只有 code 一个事实为没有）。前两问定性，第三问只决定封闭值域的升级时机，不改变定性。封闭值域落库形态：无运行时数据引用用枚举加 CHECK 约束；被运行时行真外键引用（权限点、菜单）用版本化种子表且运行时只管授予关系；属性膨胀后由枚举升级为表。枚举不能作外键目标，被运行时行引用的封闭集合不得用枚举承载。开放值域建真表加真外键供业务行引用，不建无引用的字典表；开放值域取值与展示名经该值域的列表或字典接口按请求 locale 返回，消费形态与实体 list 接口一致。代码承载形态见 mv-coding-standards java-guide「枚举与类型安全」。

### 技术栈基线

先读取当前项目构建配置、README 与已采纳 ADR；新项目选默认栈，既有项目先盘点现状，技术差异不自动触发改造。项目业务与约束的取得按「需求分析」节执行。升级是独立决策，先评估影响面再列迁移计划，不搭车业务变更。

| 类别 | 基线 | 说明 |
| --- | --- | --- |
| Java 版本 | JDK 21（LTS） |  |
| Java 框架 | Spring Boot 4.0.x（Spring Framework 7、Jackson 3、Tomcat 11） | 框架条款见 mv-coding-standards；Boot 3 既有项目按项目基线维护，升级走「依赖引入与升级」流程 |
| 构建工具 | Maven | 优先 mvnw 锁版本 |
| 镜像基线 | 基镜像 eclipse-temurin:21-jre、非 root 用户 10001、端口 8080 | 各栈 Dockerfile.delivery 基线，镜像定义随模块；构建与编排见 mv-delivery-standards |
| 持久层 | JPA | 禁止 MyBatis/MyBatis-Plus、tk-mapper |
| JSON 序列化 | Jackson | 禁止 fastjson、gson |
| 统一响应包络 | 基线类名 `Result`，code/message/data 三段：code 为业务错误码枚举（一场景一码）；message 走 i18n messageKey；data 为强类型响应载体 | 新项目默认；项目既有包络连同类名优先；存量接口不擅自改造；HTTP 状态码保持语义，不一律 200 |
| 工具类库 | JDK 标准库、Spring 自带工具类与 Apache Commons | 禁止 Hutool |
| HTTP 客户端 | Spring 应用用 RestClient：优先声明式调用（Spring HTTP Interface，引擎仍是 RestClient），必须编程实现时才用编程式 RestClient；非 Spring 场景用 JDK 原生 HttpClient | 不用 RestTemplate（维护模式）；WebClient 仅响应式栈；不引 OpenFeign、Retrofit |
| 第三方平台 SDK | 平台专属 SDK 默认不引：RestClient 直连 + 签名/验签自封装；行业标准协议的事实标准客户端放行（S3、SFTP、SMTP 等） | 试金石：换同类供应商客户端要不要跟着换；自封装签名配单测，平台测试环境联调验签通过为完成门；测试环境信息取得见 mv-coding-standards 的外部调用条款；真引入才写 ADR 并加防腐层 |
| 数据库 | PostgreSQL | dev/prod 统一，开发联调直连远程 |
| SQLite | 仅限单测、临时验证 | 不作开发联调库，无双方言兼容要求 |
| 缓存与分布式锁 | Redis | 按需引入，实例不开启持久化、不在备份范围；dev 可使用跨项目共享实例并按项目隔离，UAT、prod 等其他环境按项目和环境隔离实例 |
| 消息队列 | RabbitMQ | 其他中间件按需引入，先过「依赖引入与升级」 |
| 对象存储 | RustFS（S3 兼容） | 统一用 S3 兼容客户端接入 |
| 文件传输 | SFTPGo（SFTP） | 不使用明文 FTP |
| AI 能力接入 | magpie 网关 | `baseUrl` `http://127.0.0.1:3425/v1`、`apiKey` `magpie`，不向用户另行索取；用户或项目文档明确给出其他连接信息时以所给为准 |
| LLM 应用框架 | Spring AI | 不引入 Spring AI Alibaba；模型接线统一用 OpenAI 兼容 starter（`spring-ai-starter-model-openai`），不引入 provider 专属 starter/SDK，不自研 HTTP 客户端直连模型 API；换模型只改配置 |
| 前端形态与脚手架 | 按角色分为管理端与用户端；用户端可包含网页、H5、小程序或 App，按项目需要选择。Web 工程固定以 shadcn-admin + Vite + React + TypeScript 为基线，使用其 TanStack、Tailwind 与 shadcn/ui 底座；用户网站、用户后台（Portal）和运营管理后台按各自任务定制布局；用户端小程序与移动端 H5 统一使用 Taro + React + TypeScript，按需编译小程序与 H5；App 使用 H5 时按项目要求选择原生壳并验证平台能力 | 工具链安装见 mv-toolchain-manager，编码规范见 mv-coding-standards（按框架应用），项目初始化见本 skill「新项目初始化」；React、TypeScript、shadcn/ui 为前端基线技术 |

Taro 是使用 React 等语法开发跨平台应用的框架，按目标平台构建小程序与 H5；H5 是网页，不自动生成原生 App。需要上架或使用推送、支付、相机等能力时，先确认目标平台支持情况、壳与原生桥接方案，并在目标设备验证。

用户后台和运营管理后台是前端界面，后端是提供接口和业务能力的服务，术语与边界见本节「术语」。用户端公开网页与 Portal 可共用 Web 工程并区分布局、路由与权限；有独立发布或技术需求时可拆分工程，均按 Web 基线初始化。

新项目从基线默认选起，偏离基线记录理由并产出简版 ADR；选型决策要点见 [references/baseline-template.md](references/baseline-template.md)，基线未覆盖的类别按同一流程补齐。

### 依赖引入与升级

- 新增依赖版本对齐项目既有依赖管理（BOM / version catalog），不在构建文件散落单点版本号；优先复用已用库的既有能力，引入新库说明理由、维护状态与退出成本，License 与安全核对后再进，供应链扫描与漏洞处置按 mv-security-standards 执行。
- 升级安全补丁与 LTS 优先；破坏性升级独立分支，先评估 API、依赖与数据迁移影响并列迁移与回滚计划；升级后按项目管线验证（出包、部署、回归）。

架构方案产出：简版 ADR（一项决策一份）、架构评审记录（结论、风险、开放问题、责任人）、需要回填到 HLD/LLD 的约束清单；未确认的规模、合规与集成细节标 `TBD` 或 `Open Question`，不编造取值。选型产出简版 ADR，盘点产出现状清单，升级产出迁移与回滚计划；基线偏离显式标注理由。

## 工程文档与图件

将工程文档与图件作为独立交付物产出，而不是当前对话的延伸。按交付物分三个任务模式；一项任务跨模式时按「写作编排内容 → 制图产图 → 插图编排进文档」顺序完成，不把中间产物误作交付完成：

- **写作模式**：文档内容与结构——新建、局部修订、重写、评审。
- **制图模式**：可编辑图源与本地渲染成品图片，图本身即交付物，不管图最终进不进文档。
- **插图编排模式**：把图源或成品图放进 Markdown/Word/PPT——插图、换图、尺寸与位置控制、图文一致与文档内核验。

### 写作模式

#### 核心流程

1. 确定任务模式：
   - 新建（Create）：依据需求、笔记、源文件、代码或讨论产出新文档。
   - 局部修订（Update）：维护现有文档中的指定内容，并同步直接受影响的引用、表格或图；补字段、改步骤等请求默认按此模式处理。
   - 重写（Rewrite）：用户明确要求全文重写或规范化时，把既有草稿整体整理为可评审的工程文档。
   - 评审（Review）：识别缺陷、歧义、缺失决策、前后矛盾、不可验证的论断和运维缺口。
2. 从用户意图判断文档类型，适用时优先按 PRD、HLD、LLD、RFC、API 或 MOP 处理。
3. 起草前先对输入语句分类：
   - Fact（事实）：已确认的系统行为、数据、代码、配置、接口或实测结果。
   - Requirement（需求）：明确要求的行为或约束。
   - Decision（决策）：已明确选定的方案或取舍。
   - Assumption（假设）：设计所需但未经验证的条件。
   - Open Question（开放问题）：未决的决策或缺失的输入。
   - Discussion（讨论）：探索性内容，不得静默升级为需求。
4. 仅从 `references/document-types.md` 加载与本次相关的结构。生产升级/部署流程类任务同时加载 `references/mop-guide.md`。
5. 起草过程遵循 `references/quality-rules.md`。
6. 交付前执行 `references/self-check.md` 的最终检查。

只要能安全产出有用的草稿，就不为缺失细节反复追问；用 `TBD`、`Assumption`、`Open Question` 或显式占位符代替编造取值。

#### 需求澄清

需求分析、业务规则、状态流转与验收口径按「需求分析」节执行；写作前读取已有分析结果，输入不完整时按该节补齐。只改文风、章节或图件且业务语义不变时，不重新开展需求分析；缺失处标 `Open Question`，不把推测写成需求。

#### 来源忠实

当源文件、截图、工单、会议纪要、代码或用户提供的文本是文档依据时：

- 只陈述来源能够支撑的内容。
- 保留既有的术语、标识符、端点名、配置键、版本号和职责边界。
- 不静默修正、调和或扩展来源未支持的内容。
- 补充外部知识或推理时，与来源推导的内容明确区分。
- 除来源本身是应列入 `References` 的正式引用外，最终文档不暴露源文件名、聊天记录或起草过程。

#### 内容规则

- 文档脱离当前对话仍可独立理解。
- 使用客观的工程语言。
- 同一概念全文使用同一个稳定术语。
- 需求与实现选择分开；决策与备选方案、未决问题分开。
- 关键论断在有证据（代码、配置、接口、需求、数据、日志或正式引用）时可追溯到证据。
- 宁可显式标注未知，不用看似合理的补全。
- 设计决策有明显成本或风险时给出权衡。
- 范围可能被扩大时给出 `In Scope` 与 `Out of Scope`。
- 不为“看起来完整”添加空洞章节。

#### 默认文风

默认使用中文工程书面语，用户另有要求除外。

- 不用“我们”“你”“您”等人称措辞。
- 不用“根据您的要求”“以下是”“结合之前讨论”“本次调整”等对话痕迹用语。
- 不用“高性能”“高可用”“先进”“优雅”等无依据的夸饰。
- 不用“搞”“弄”“东西”“到时候”“回头”“搞定”等口语。
- 中英文与数字边界保持可读，如 `TLS 1.3`、`P99 18 ms`、`Redis 集群`。
- 优先朴素的 Markdown；不用装饰性 emoji、过量强调和装饰性分隔线。
- 架构、流程、时序用图能显著提升理解时使用 Mermaid。

#### 文档类型行为

##### PRD

聚焦问题、目标用户/角色、目标、范围、需求、验收标准、依赖和开放问题。不把实现想法过早写成需求。

##### HLD

聚焦系统上下文、架构、组件、边界、接口、数据流、部署拓扑、主要非功能约束、故障域和关键权衡。实现细节保持在架构评审所需的层次。

##### LLD

按 [LLD 规则](references/document-types.md#lld) 读取输入、展开流程、建立需求到设计与测试的追溯，并记录阻塞项和就绪状态；交付前按 [最终质量门](references/self-check.md) 检查。仅在任务要求或项目约定需要详细设计时编写 LLD。

##### RFC

让决策过程显式化。包含问题、目标/非目标、方案、已考虑的备选、理由、影响/权衡、兼容性/迁移、风险和未决问题。决策未定时写 `Decision: TBD`。

##### API 文档

精确描述契约行为：用途、端点或 RPC 名、方法、路径、认证、请求字段、响应字段、状态/错误码、校验规则、幂等、示例，以及来源支持的兼容性/版本策略。绝不虚构请求字段或错误码。

##### MOP

升级/部署 MOP 是可执行的生产变更操作文件，不是泛泛的升级介绍。仅在已确认时包含前置条件、变更范围、准备项、备份、逐步命令/动作、检查点、成功标准、回滚触发条件、回滚步骤、变更后验证和责任人。加载 `references/mop-guide.md`。

##### ADR

架构决策记录的内容判据与模板见「架构与选型」（references/adr-template.md）；写作模式只在 ADR 作为交付文档时负责结构与文风，不另造决策模板。

#### 局部修订行为

- 起草前确定修改目标及直接影响范围，沿用既有章节、编号、术语与文风，保持已确认的需求、设计与接口语义。
- 文档类型模板用于检查本次内容的必要信息，不要求旧文档补齐所有章节、重新编号或统一全文格式；不因修改某一节而重写其他章节。
- 同步修改直接受影响的字段说明、交叉引用、示例与图表，确保修订内容可独立理解并与关联内容一致。
- 质量规则与最终检查按修订内容及其直接影响范围应用；新建与明确要求全文重写时检查整个交付物。无关历史问题单列建议，不自动修订。
- 例如新增一个 API 响应字段时，同步该字段的定义与响应示例，不顺带替换 API 文档结构或补写无来源的认证与版本策略。修复相关矛盾必须扩大范围时，先说明影响并确认范围。

#### 重写行为

重写既有文档时：

- 除非用户要求变更设计，保持已确认的含义不变。
- 清除对话痕迹、无依据假设、重复章节、术语漂移和形式化套话。
- 只解决明显的结构缺陷，不改变事实。
- 除非用户要求，不输出变更日志。
- 矛盾无法依据材料裁断时，两侧都保留，并标记为 `Open Question`。

#### 评审行为

只评审不重写时，按影响分级：

- Critical：可能导致错误实现、不安全的生产执行、不兼容的 API 行为、数据丢失或不可恢复的变更。
- Major：缺失决策、前后矛盾、责任/边界歧义、关键论断不可验证、回滚或失败处理不完整。
- Minor：术语、格式、措辞、局部可读性或可维护性问题。

每条发现说明问题、影响和具体修改建议。不为展示修改能力而虚构项目事实。

### 制图模式

把已确认的事实制成规范图：物理组网图画设备与连线实体，逻辑组网图画网段、安全域与流量路径，架构图画组成部分与依赖方向，一张图只表达一个层面；时序、流程、状态、ER 等结构类图用文本图源表达。图中事实来自用户提供的资料与逐项确认，不替用户发明组件与连接。

`判定图种与要素 → 选图源 → 绘制图源 → 渲染成图 → 核验交付`

- 交付落在目标项目的 `fig-src/`（图源）与 `fig-out/`（成品图）；图后续进文档时，插图编排模式直接使用同一目录与命名约定，无需迁移。
- 制图无独立运行时状态目录，不在 `~/.mv/` 下落状态。

工作流：

1. 判定图种与要素：明确图的用途与受众（评审、HLD 附件、汇报、交付档案），按 [图种与要素清单](references/diagram-elements.md) 判定图种，并对照该图种必备要素逐项核对来源资料——设备与型号、位置分区、链路两端与端口、带宽、网段、组件与调用方向、交互顺序等。缺的要素先向用户与项目资料取得，取得不了的按「待确认」标注并说明缺什么，不编造取值。
2. 选图源：需要精确摆放的图（组网图、机架连线图、架构分层图、页面示意）用 HTML+内联 SVG，坐标由 layout_gen 从 spec 生成；时序、状态、ER、类图与结构简单的流程图用 Mermaid，需要特定 UML 语法时选 PlantUML。画法判定（通道分配、对称、布局取舍）按 [图面语法](references/visual-grammar.md)，画法与渲染细节按需读取 [SVG 图源与渲染](references/svg-diagrams.md)。
3. 绘制图源：精确摆放的图先写 spec（JSON，格式见 `layout_gen.py --help`），运行 `python3 "${SKILL_ROOT}/scripts/layout_gen.py" spec.json "fig-src/<图名>.html"` 生成自包含图源；本机无 mermaid CLI 时时序图用 layout_gen 的 sequence 模板。生成器断言失败（文字超宽、直落不在目标框内等）按报错回改 spec 重跑，不绕过；生成器未覆盖的局部才在产物上手调，手调不破坏网格与间距。图源不引用外网资源，组件与链路命名与用户资料术语一致。修改先改 spec 或图源。
4. 渲染成图：优先使用当前会话已配置的浏览器预览/截图能力；无该能力时用 `render_diagram.sh` 发现本机 Chrome/Edge 无头渲染，窗口尺寸与图源画布一致，倍率按目标用途设定（评审与文档用图 ≥2x）。浏览器缺失时如实报告缺失，保留图源并注明未渲染，不虚构成品。
5. 核验交付：打开成品核对文字不溢出、连线不穿节点、图例完整、方向一致，并逐项回对来源事实；交付说明写出图源与图片位置、依据哪些资料、待确认要素清单、渲染方式与核验结果。

制图硬约束见「硬约束」节的制图与插图编排部分。

### 插图编排模式

负责图在目标文档中的放置与验证：插图、换图、尺寸与位置控制、图文一致与成品核验；文档正文、结构和事实核验由写作模式负责，图的绘制与渲染由制图模式产出（`fig-src/` 与 `fig-out/` 命名对应）。

工作流程：

1. 确定文档格式、图的目的与插入位置，核对成品图与正文术语一致。已有文件先查看目标页、段落或形状，明确图尺寸；图标编号与图注由写作模式维护。
2. 需要新图时，先走制图模式完成可编辑图源与成品图片；已有图或已有截图直接进入放置。按需读取 [渲染指南](references/rendering.md) 做文档侧嵌入判定与图片核验。
3. Markdown 在目标阅读器支持时可直接嵌入 Mermaid 源码，否则引用已渲染的本地图片。Word/PPT 使用已渲染的 PNG，在**写作文档的同一任务中**插入成品，不把制图完成误作交付完成。
4. 对新建的 Word/PPT，先用该格式的文档制作能力生成正文或幻灯片，再在确定的位置插图；对已有文件先列举目标图或设置唯一锚点，再插入或替换。按需读取 [Office 配图指南](references/office-figures.md)。本模式脚本编辑图形，不生成任意正文或整套幻灯片。
5. 写出新的文档文件后，复查图文一致、图注、比例、位置、裁切、与页面背景的对比和文件可打开性。能使用目标应用时逐页查看；只运行了 ZIP/XML 检查时如实记录尚未进行视觉检查。

### 产物组合

用户明确要求 DOCX、PDF、幻灯片等渲染产物时，先由写作模式确定内容与结构，再用相应的能力生成目标文件格式。写文档需要配图时，写作模式编排内容并核对图文事实：先制图模式产出可编辑图源与渲染成品，再由插图编排模式插入并核验；Markdown 正文中的内联 Mermaid 块属于正文写作，由写作模式直接撰写。上游业务梳理（端到端业务流程、规则与验证场景）按「需求分析」节执行，依据当前项目材料与确认记录产出；材料缺失处按 `TBD` 与 `Open Question` 标注，不自行编造业务流程。

## 新项目初始化

面向新项目的从零到可运行骨架：仓库布局、所需应用初始化、交付与环境配置一次落位。技术栈定版之后的业务编码、既有项目的常规功能开发不归本 skill。初始化产出的骨架持续遵守 mv-coding-standards，不重复其条款；优先级：用户明确需求和项目已采纳的规范 / ADR → 「架构与选型」的技术栈基线 → 生态默认。

### 开始前确认

先按「需求分析」的项目上下文条款读取已有项目上下文，复用已确认的范围与业务约定；初始化不重新定义业务模型。开始前确认：项目名与应用名（APP 名，部署侧同用）、需要的后端、角色端（管理端、用户端）与用户端载体（网页、H5、小程序等）、仓库形态（单仓多模块或多仓）、基础设施范围（是否需要 PostgreSQL、Redis、RabbitMQ、RustFS）。只对会影响本次初始化且资料中缺失的决策补充确认，不默认全量端全量设施。纯前端、无数据库或已有后端的任务只初始化所需部分，不附带新增 Spring Boot、数据库或认证系统。

### 仓库布局判据

系统形态（单体、按端切、按域切、微服务）按「架构与选型」的形态判定条款判定；用户后台与运营管理后台指前端界面，用户端后端与管理端后端指服务，术语见该节。本节只负责把选定形态落成目录与模块。

1. 单仓多模块为默认：多数双端项目共用 `<project>-service` 和 `<project>-web`，内部按路由、布局及权限区分两端；面向 C 端消费者且同时有两端的产品默认分离 `-user-service`、`-admin-service` 和实际需要的前端工程，分别部署。例外按「架构与选型」记录理由；单端项目只建需要的端。
2. 出现独立团队、独立发布节奏或独立访问控制的模块才拆多仓，不为「看起来干净」拆仓。
3. 模块与目录命名按 mv-coding-standards 模块命名闭集执行：目录名即模块名，端词固定占用 `admin`（管理端）、`user`（用户端），不与域词混用。
4. 后端接口契约是类型真源；有跨项目集成时才按消费者需要拆 api 模块，分端契约可命名 `-user-api`/`-admin-api`。前端类型从契约生成或集中映射，不在页面重复手写后端字段。

### 初始化步骤

只执行已确认范围对应的步骤；后端、各前端、数据库与基础设施均按实际需要落位，不把完整示例当作每个项目的必建清单。

1. 建仓库：执行 `git init`，默认分支 `main`，开发分支 `dev`。初始化不自动授权提交；用户未明确要求提交且项目未确认提交授权时继续搭建骨架，保留工作区与暂存区。用户明确要求首次提交或项目已确认首次提交授权时，首个提交为空提交并在 `main` 先行推送，命令与固定提交消息按 mv-git-publisher「新仓库首次提交与推送」执行；推送后创建并切换 `dev` 分支，README、骨架代码等内容提交在 `dev` 进入。
2. 后端骨架：Spring Boot 4 + JPA + PostgreSQL + Flyway 首迁（V1 建表与种子数据）、统一包络、readiness/liveness 双探针、错误码枚举与双语资源骨架、`.dockerignore` 与 `Dockerfile.delivery`（基线镜像 eclipse-temurin:21-jre、非 root 10001、端口 8080）；模块划分按「仓库布局判据」。
3. 运营管理后台界面：共用 Web 时在同一工程内初始化管理路由与布局；独立时初始化管理端工程。以 shadcn-admin 为基线起步（Vite + React SPA + TanStack + Tailwind），衍生清理（faker 演示数据、Clerk 认证替换、示例路由）按 mv-coding-standards 的 Vite SPA 条款执行；对接后端包络与 RBAC 权限点。
4. 用户端网页（按需）：确认公开网站与用户后台（Portal）的范围；共用 Web 时在同一工程内初始化相应路由、布局和权限，独立时初始化用户端网页工程。用户网站与用户后台均以 shadcn-admin + Vite + React + TypeScript 为基线，按用户任务定制布局；网站和 Portal 可共用工程或按独立发布、技术需求分开。
5. 用户端 H5/小程序（按需）：统一使用 Taro + React + TypeScript，按项目需要编译小程序与移动端 H5；App 使用 H5 时按项目确定原生壳与平台能力并逐项验证。工程条款见 mv-coding-standards 的 Taro 条款。
6. 环境配置：本地开发联调默认连接开发服务器的公共 infra（PostgreSQL、Redis、RabbitMQ、RustFS、SFTPGo 按项目需要接入），按 [仓库布局参考](references/repo-layout.md) 的本机公共 infra 配置产物流程读取用户预填信息，仅询问本次缺项、写回已确认的非秘密信息并申请项目专用资源和凭据；业务进程在宿主启动，不为每个项目重复创建基础设施编排。`.env.example` 只记录配置键与占位值并纳入版本控制，真实 env 文件保持未跟踪。`.gitignore` 忽略 `.env*` 并以 `!.env.example` 放行样例。
7. 首次迁移与种子数据：需要数据库的项目建立 V1；已确认的 RBAC 权限点、菜单及字典按实际范围加入种子数据（幂等 upsert），与代码同版本发布。种子脚本不含任何账号凭据：有后台项目的初始管理员由启动期初始化器按环境变量注入（见 mv-security-standards「认证」），无后台工具端不建用户表、用内存用户认证。不预置订单、会员、支付等未确认业务表，也不为无管理端的项目创建演示菜单。
8. CI 样例：PR 触发「编译 + lint + 单测」工作流样例（GitHub Actions），作为项目最小门禁起点，按项目演进调整。
9. 本地验证：宿主前台直启跑通每个后端入口与前端工程（前台可见窗口运行、Ctrl-C 可停），逐入口验证配置、探针和对应端联调，记录「编译/启动/首屏」证据后收尾。

初始化产出可运行的骨架仓库（端按需）、env 样例与 CI 样例；需要数据库时产出首次迁移。交付说明记录布局形态与理由、公共 infra 接入和隔离方式、偏离基线项及对应 ADR、各端本地验证证据、未初始化的端与原因。

## 硬约束

- **业务规则须能追溯到当前项目来源或明确确认；示例与假设不写成已确认需求。**
- **规则冲突列明来源、差异与影响，由有权确认需求的角色裁决，不静默选取其一。**
- 验收覆盖业务结果与关键失败路径；页面可打开、HTTP 200、容器健康均不能代替业务验收。
- 法规、资质、数据保留期、性能阈值与 SLA 先核对项目适用范围及依据，不给所有行业套用同一数值或宣称合规。
- 需求确认、测试通过与上线批准分别记录；产出文档不代表获得业务确认或发布授权。
- **版本与依赖一律取自「架构与选型」的技术栈基线**，不引入基线外依赖；确需偏离先走选型流程产出简版 ADR。
- **环境变量样例不含真实密钥**，占位值即可；真实凭据经运行时注入，不进仓库；数据分级与凭据要求按 mv-security-standards 落位。
- **初始化不连生产**：全流程只接触本地与开发环境。
- **提交须由用户明确要求或取得项目已确认的提交授权**；首次提交为空提交并先行推送，不夹带文件。

### 制图与插图编排硬约束

- **先要素后画图**：组件、连接与标注必须来自用户确认的资料；缺要素的链路标「待确认」并说明缺什么，不编造端口、IP、带宽、网段。
- **物理与逻辑不混画**：同一张图不同时表达设备实体与网段/流量语义；确需对照时画两张，图元命名保持对应。
- **图源可再生成**：交付必须含可编辑图源；只有 PNG 不称可编辑图源；修改先改图源再渲染，不直接修改成品图。
- **先算法后坐标**：精确摆放的图必须先写 spec 由 layout_gen 生成，禁止无算法徒手摆坐标；状态、ER 等带环路的图交给 Mermaid/PlantUML 自动布局，不用本生成器硬画。
- **本地渲染**：不把含真实组网信息的图源上传在线渲染服务；不使用隐式联网安装依赖的 `npx`。
- **披露最小化**：内网地址、设备型号按用户披露范围呈现，不向图外扩散；产物只写在用户项目内。
- 换图先换保留的图源并重渲染（制图模式的渲染流程），不直接修改成品图；真实页面截图保持来源与时间可追溯。发现成品图与正文事实不一致时停下核对来源，不为版面美观补造或修改图的内容。
- 处理含敏感信息的图不上传在线服务。依赖缺失时报告缺失，不默默调用会联网安装依赖的 `npx`。
- 保持目标格式可用。Office 文件只能向**不同的输出路径**写入；先预览定位候选项，目标不唯一时停止，绝不以“图注前最近一张图”自动修改。
- Word/PPT 替换只改变被选中的一张图；即便几处共用同一媒体文件，也不能覆写原媒体使其他位置一起变化。
- 不把 Markdown 的 Mermaid 块直接当作 Word/PPT 图片交付；图源、图片、目标文档三者均应存在且对应。
- 冲突时按用户明确需求 → 本规范 → 工具默认行为处理；用户指定的图源格式、布局和现有项目约定优先。

## 输出与边界

各子领域产物在其小节内写明；验证结果如实记录，未执行的检查明确写「未执行」，不写成「通过」。评审交付物按 Critical / Major / Minor 分级记录发现。

跨 skill 边界：业务代码与测试的分层、写法、执行与证据归 mv-coding-standards；镜像构建、容器部署、compose 编排与交付管线归 mv-delivery-standards；交付后稳态运维归 mv-ops-standards；安全政策、数据分级、威胁建模与供应链处置归 mv-security-standards；本机工具链检测安装与版本切换归 mv-toolchain-manager；提交信息、PR 描述等 Git 短文本归 mv-git-publisher。本 skill 确定需要验证的业务行为，不执行项目管理平台写入或代替业务方审批；数据图表与网络方案设计不归本 skill，不负责通用 Word/PPT 正文或幻灯片排版；基线与项目实际冲突时项目优先。
