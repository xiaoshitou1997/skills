# 编排编写细则

mv-orchestration-standards 关键规则 2-5、8-9 的展开：命名、网络、端口、镜像、YAML 键序与数据卷形态。与项目已确立基线冲突时以项目为准。

## 栈命名

- 栈名 = 目录名 = compose 项目名 = 产品名小写，符合 DNS-1123 label：小写字母数字、连字符分段，不允许大写、下划线、驼峰及首尾/连续连字符。
- 取官方产品名的小写形式并保留官方连字符（`Open WebUI` → `open-webui`），目录名与官方名一致，不强行拼接、不建「官方名 ↔ 拼接目录」映射记忆。
- 跨产品的功能聚合类目录用语义词小写（如 `gateway` 表示网关聚合栈）；环境后缀按「环境即栈」铁律直接入栈名（`halo-dev`、`halo-prod`）。
- 本条只约束目录/栈名：service 名、volume 名、镜像名等内部标识保持原样；网络名由栈名派生（`{栈名}-net`）随栈名同步。
- 容器名不设 `container_name`，由 compose 自动生成 `{项目}-{服务}-1`；命名卷实际卷名 = `{项目名}_{卷名}`，各栈天然隔离——该隔离依赖不设顶层 `name:`，禁止任何栈覆盖 compose 项目名；`docker volume ls` 中无项目前缀的裸卷名只可能来自手动 create，应删除。

## 网络

- 显式声明 `networks.default.name: {栈名}-net`。
- 通信路径判定（逐连接自上而下，命中即停）：
  1. 双方在同一 compose → 服务名直连（如 `app` 访问 `mysql:3306`）。
  2. 双方在不同 compose → 共享 external bridge 网络；不得经 `host.docker.internal`、宿主机发布端口或 localhost 绕行。
  3. 目标是宿主机原生进程（不在容器里）→ 允许 `host.docker.internal`，且仅此时声明 `extra_hosts`；为「将来可能用」保留属投机配置，禁止。
- 通信路径不固定的依赖（可能同机也可能跨机）：地址经 `.env` 注入，compose 用 `KEY: ${KEY}` 透传、config/CLI 写 `${VAR}` 占位；不硬编码目标栈服务名或具体地址；栈可用性不得依赖与目标栈同机。

## 端口判定

逐服务自上而下，命中即停：

1. 由外部反向代理终结 TLS → 后端只发布 HTTP 端口；反代与后端按共享 external 网络通信。
2. 栈内数据库/中间件 → 不发布端口，映射以注释声明（保留注释便于按需开启）。
3. 官方文档给了 host 端口示例 → host 端口 = 示例值。
4. 无示例 → host 端口 = 容器内官方监听端口。
5. 同一 compose 内多服务端口相同 → 后者依次 +1（如 `5432:5432`、`5433:5432`）。
6. 跨栈端口重复 → 不处理，按需启停。

有记录的偏离：确因运维需要偏离判定（统一 HTTP 直连、规避自签证书告警等）时允许，但必须在 ports 对应行行内注释写明原因；无注释的偏离视为违规，注释即决策记录。

## 镜像

- 全部固定具体版本：禁 `latest`、`main`、无标签。
- 有 Alpine 变体一律用 Alpine，不兼容时按步骤退官方变体并注释：Java 应用依赖 glibc → musl 可能不兼容，改 `-slim`/`-jre` 变体；Python C 扩展需本地编译 → 用预编译轮子或 `python:3.x-slim`。
- 晋级使用已验证的同一镜像身份；验证、发布与回滚期间各环境可暂时运行不同版本。基础设施镜像升级分别评估兼容性，跨项目同类型服务版本各自固定。
- 上游官方仅维护 latest 且无版本标签的镜像，允许 `latest`；继续使用已 EOL/停止维护的版本时，在 image 行行内注释登记理由与评估日期。

## YAML 写法

- `command` 用内联列表（`["--log-dir", "/app/logs"]`）；`environment` 用 map；`volumes`/`ports` 用列表。
- service 内键序：`image → privileged → command → environment → volumes → ports → networks → extra_hosts → init → shm_size → stop_grace_period → secrets → healthcheck → depends_on → logging → restart → deploy`；顶层键序：`volumes → networks → secrets → services`；没有的键跳过。
- 不加多余注释，删除注释掉的配置行；例外保留：端口不发布声明注释、偏离记录注释、environment 分块标题注释。

## 环境变量声明与标注

- 按需声明：只声明本部署实际需要的变量，不整表枚举镜像支持的全部变量。
- 分块：env ≥ 4 条且分属不同功能关注点时按功能分组，组间用 `# ── 块名 ──` 注释；env < 4 条或同属一个关注点不分块。
- 变量后一律不写行内注释：配置错误绝大多数是部署期响亮故障，日志可定位；静默型陷阱以官方文档核对与部署后校验承担。
- 一切以官方文档为准：新增配置前查当前锁定版本的官方文档确认变量名、取值与默认值；不凭记忆回答「有没有这个配置」。
- 环境变量优先、单一渠道：参数有官方专属环境变量时经 compose `environment` 注入并从 config 删除该参数；仅无专属环境变量的参数才在 config 中引用（如 `os.environ/`）；同一参数不得双渠道同时出现。
- 升级镜像版本时逐个对照新版官方文档复核已声明变量：改名同步改键名、废弃直接删除（不留注释行，历史查 git）；拿不准是否废弃就删——回归默认的风险低于残留失效配置。

## 禁止自定义 entrypoint / 启动注入

- 使用镜像官方 entrypoint/cmd：禁止为「启动前改配置」自建包装脚本（先改写配置再 exec 官方入口一类）——与官方配置管理机制打架，升级即碎。
- 配置走组件官方渠道：有 Web UI 的在 UI 操作并持久化到卷；文件驱动的用官方约定指向挂载文件；环境变量方式经 compose 插值。
- 发现为某组件写了非官方启动包装/转换脚本时，视为信号：回归官方配置方式，删脚本而不是继续维护。
- 官方部署文档/compose 示例给出的 entrypoint 不属禁令范围。

## 数据卷

- 默认命名卷，声明在顶层 `volumes`；仅两类例外用 bind（逐条命中即停）：
  1. 配置文件要预置于仓库随部署走（JSON/YAML conf），路径必须确定 → bind。
  2. 挂载宿主机既有资源（`/var/run/docker.sock`、宿主机代码目录），命名卷无法表达 → bind。
  3. 以上皆无 → 命名卷；宿主机要读运行态用 `docker exec` 或临时容器，不作为 bind 理由。
- 命名卷写入权限以实际挂载点与镜像运行 UID/GID 为准，先核对镜像官方初始化机制及目录属主，再采用官方支持的卷初始化、预设属主/组或存储驱动权限配置；初始化与应用运行分离，应用保持非 root。初始化需提权时使用最小范围、一次性操作并记录，完成后验证应用 UID/GID 能写目标目录且不能写无关目录；无法满足时停止并报告，不以 `user: "0:0"` 作为应用运行期兜底。
- 不为「数据要持久」选 bind——命名卷同样持久（down 不删卷）；两者唯一区别是路径归谁定。官方示例的形态不作为判据。
- bind 源路径用 compose 相对路径（`./xxx`）或绝对路径，禁 `~`（随执行用户展开，伪确定性）；同一栈内不混用两种形态指向同一数据。
- 卷名后缀判定：`-data` = 服务主数据目录（数据库文件、对象存储、业务数据，删卷即数据尽失，备份以它为准）；`-home` = 运行期 HOME 类状态目录（配置、凭据、会话、插件，挂载的是进程 HOME 或配置根）。看容器内挂载路径是否进程 HOME/配置根；单卷服务一律 `-data`。
