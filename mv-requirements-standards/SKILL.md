# 需求规范

面向 MV 团队各项目的需求分析与变更评审，产出可实现、可验证的业务约定。行业规则以当前项目的来源与确认记录为准，文档排版和技术方案由对应 skill 承担。

## 作用与优先级

这是**规范型 Skill**，在需求梳理、业务规则分析、验收定义与需求变更时使用。优先级：用户明确需求和项目已确认约定 → 本规范 → 分析模板；来源冲突显式列出，不将旧项目规则、通用行业经验或当前代码行为自动视为新需求。

需求分析按变更规模裁剪：小变更补受影响的规则和验收即可；新系统或跨流程变更再建立完整上下文，不要求每次填写整套模板。

## 工作流程

1. 确定当前项目与任务范围：新建、存量接管、新功能或需求变更；按 [项目上下文](references/project-context.md) 读取现有项目资料，记录本次涉及的角色、系统、数据和约束。团队技术栈为默认方案，项目选型偏离交 mv-tech-stack-baseline 处理。
2. 整理来源与状态：区分已确认需求、现状事实、讨论建议、假设与开放问题；记录来源及确认人或待确认角色。现有代码只能证明当前实现，不能单独证明客户要求。
3. 定义目标与范围：写清业务问题、可观察的成功判据、本期交付与排除项；列出业务方、使用方、验收方和外部系统责任边界。缺少具体人名时记待指定角色，不编造责任人。
4. 建立术语、流程与规则：按 [业务规则](references/business-rules.md) 描述主流程、异常、状态迁移、数据口径与人工介入点；仅为已确认的角色与能力建立模型，不预设订单、会员、支付、多租户或审批中心。
5. 定义验收：按 [验收与变更](references/acceptance-change.md) 将每条独立需求映射到输入、动作、可观察结果与证据；功能、安全、性能和恢复目标按实际风险补充。数值阈值需有来源或显式标为待确认。
6. 处理未决项：区分阻塞实现的业务决策与可继续的独立工作；金额计算、授权范围、状态终态等未决时先保留接口或草稿，不编造规则实现。非阻塞信息先标注并继续，不重复索取资料已有的答案。
7. 评审与交接：记录范围、规则、验收及未决项的确认状态；按影响转交架构、编码、安全与测试规范。需要正式 PRD、流程图或评审稿时配合 mv-engineering-doc-writer；只要求梳理需求时直接交付分析结果。

## 硬约束

- **业务规则须能追溯到当前项目来源或明确确认；示例与假设不写成已确认需求。**
- **规则冲突列明来源、差异与影响，由有权确认需求的角色裁决，不静默选取其一。**
- 验收覆盖业务结果与关键失败路径；页面可打开、HTTP 200、容器健康均不能代替业务验收。
- 法规、资质、数据保留期、性能阈值与 SLA 先核对项目适用范围及依据，不给所有行业套用同一数值或宣称合规。
- 需求确认、测试通过与上线批准分别记录；产出文档不代表获得业务确认或发布授权。

## 输出

按任务规模产出需求条目、术语与业务规则、流程或状态表、验收标准、来源与确认状态、假设与开放问题；变更任务追加影响范围和需要重新确认的验收项。沿用项目已有编号或工单标识，只为可独立交付或验收的需求新增标识，不另造平行台账。

## 边界

正式文档的内容组织、文风与图件归 mv-engineering-doc-writer；技术栈与依赖选型归 mv-tech-stack-baseline；系统形态、服务边界与一致性方案归 mv-architecture-standards；业务实现归 mv-backend-standards 与 mv-frontend-standards；测试设计、执行与证据归 mv-test-standards；安全评审与数据保护细则归 mv-security-standards。本规范确定需要验证的业务行为，不执行项目管理平台写入或代替业务方审批。
